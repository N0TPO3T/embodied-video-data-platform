# Embodied Video Data Platform 代码审计报告

## 1. 审计结论

项目已经具备较完整的本地业务闭环：账号和团队权限、分片上传、媒体处理、AI 质检、人工复核、积分周期、交付包、对象治理及审计日志均有实际后端实现，且现有自动化测试整体质量明显高于普通原型项目。

但当前版本不建议直接按“规则可运营、任务可长期无人值守、统计可作为结算依据”的标准投入正式运行。审计确认 **5 个高优先级问题、6 个中优先级问题和若干低优先级工程问题**。最关键的风险是：

1. 管理端发布的质量规则、积分规则和标签版本没有真正驱动核心计算，且 AI 与人工复核使用的质量系数不一致。
2. RabbitMQ 重复投递媒体任务时，已完成任务可能被改回 `awaiting_ai` 并永久停住。
3. 交付归档任务仅由 API 进程内的异步函数执行，服务重启或审计写入失败会留下永久卡住的任务。
4. 完全重复视频只靠“先查再写”，并发上传可以绕过；后续 AI 检测同样存在并发窗口。
5. 多个运营和团队指标只基于最新 100 条数据计算，数据超过 100 条后会静默失真。

建议先完成 P1 修复，再进行真实部署演练和长时间压测。

### 风险等级

- **P1 / 高**：可能造成计分错误、任务永久卡住、重复结算、核心运营数据错误，正式运行前应修复。
- **P2 / 中**：存在安全、稳定性、扩展性或恢复能力缺口，应进入近期迭代。
- **P3 / 低**：工程治理或部署加固问题，可结合上线准备处理。

## 4. 详细发现

### F-01（P1）：规则版本与实际业务计算脱节

**证据**

- `backend/src/ai-quality/ai-quality-analysis.service.ts:292-305` 仅把质量规则和标签版本的 ID、revision 写进质检结果；创建 evaluator 时没有把规则内容或标签内容传入。
- `backend/src/video-quality/video-qc-rule-engine.ts:34-38` 使用固定系数：80 分以上 1、60 分以上 0.8、40 分以上 0.6、否则 0.4。
- `backend/src/submissions/submissions.service.ts:86-90` 人工复核使用另一套固定系数：80 分以上 1、70 分以上 0.85、60 分以上 0.7、否则 0。
- `backend/src/points/point-cycles.service.ts:337-343` 把通过线固定为 60；`384-390` 直接使用已经保存的 `settlementRatio`。
- `backend/src/points/point-cycles.service.ts:219-230` 在候选和总分已经计算完之后才读取积分规则，随后只把规则版本 ID 写进周期。
- `backend/src/points/point-rules.service.ts:107-199` 保存的 `defaultPointsPerMinute` 和 `coefficientBands` 没有进入周期计算。

**可复现场景**

- 管理员把通过阈值从 60 改为 70，65 分视频仍会进入积分候选。
- 同一条 65 分视频，AI 自动结果系数为 0.8；管理员人工复核后系数会变成 0.7。
- 管理端发布新的积分系数分段后，历史之后的新周期仍沿用代码中的固定逻辑。
- 更新标签名称或启停状态只会生成版本快照，不会改变发给模型的标签上下文。

**修复建议**

建立单一服务端规则计算器。AI 任务开始时锁定完整的质量规则和标签快照；最终分、通过状态、质量系数和积分必须由该快照统一计算。积分周期应使用锁定的 `PointRuleVersion` 内容计算，而不只是保存其 ID。为 59/60/65/69/70/79/80 等边界值增加端到端测试，并验证“发布新规则只影响新任务/新周期”。

### F-02（P1）：媒体消息重复投递会破坏已完成任务

**证据**

- `backend/src/media/rabbit-media-worker.ts:99-102` 先完成全部媒体处理，再 ack 消息；进程在数据库提交后、ack 前退出时，RabbitMQ 会重新投递。
- `backend/src/media/media-analysis.service.ts:125-139` 只校验 `uploadStatus === uploaded`，不会跳过已经 `completed` 的提交，也没有按 submission 加锁。
- 同一服务在 `backend/src/media/media-analysis.service.ts:217-236` 无条件把提交改成 `awaiting_ai`，再用 `orIgnore()` 插入 AI outbox。
- `backend/src/database/entities/job-outbox.entity.ts:14-16` 对 `(eventType, aggregateId)` 有唯一约束。原 AI 事件若已经是 `published`，上述插入会被静默忽略。
- `backend/src/ai-quality/ai-quality-analysis.service.ts:155-160` 又会跳过已有终态质检结果。因此已完成提交可能被改回 `awaiting_ai`，却没有新的 AI 消息可以把它恢复为完成。
- `backend/test/media-analysis.e2e-spec.ts:279-298` 只验证了顺序重复调用，不覆盖“AI outbox 已发布且质检已终态”的场景，也不覆盖两个 Worker 并发处理同一 submission。

**修复建议**

媒体处理入口应使用 submission 级 advisory lock 或带条件的行锁，并根据合法状态机更新：终态默认直接返回；只有显式重跑才能创建新 run。消息和结果引入 `runId/generation`，所有更新都校验 generation。重排队时应显式把既有 outbox 事件更新为 `pending`，而不是依赖 `orIgnore()`。增加“提交后崩溃再投递”“两个 Worker 同时收到同一消息”“AI 已完成后收到旧媒体消息”测试。

### F-03（P1）：交付归档任务无法跨进程恢复

**证据**

- `backend/src/delivery/delivery-packages.service.ts:599-611` 先把任务保存为 `queued`。
- `612-625` 使用独立数据库写入审计，不和任务创建处于同一事务。
- `626` 通过 `void this.processArchiveTask(...)` 在当前 API 进程内启动异步工作。
- `756-849` 才是真正的归档逻辑；项目中没有启动扫描、租约、超时恢复或消息队列消费者来重新领取 `queued/processing` 任务。

**影响**

- API 在任务保存后、异步函数启动前退出，任务永久停在 `queued`。
- 归档过程中 API 重启，任务永久停在 `processing`。
- 审计写入失败时接口返回失败，但任务已经存在且后台处理尚未启动。
- 多个大归档由 API 进程直接并发执行，会同时占用本地磁盘、MinIO 带宽和 Node 进程资源。

**修复建议**

把归档改为 outbox + 专用 Worker，或至少实现数据库租约队列（`FOR UPDATE SKIP LOCKED`、attempt、leaseUntil、heartbeat）。任务创建和审计应在一个事务内；Worker 启动时领取 `queued` 及租约过期的 `processing` 任务。增加进程重启恢复和重复领取幂等测试，并限制全局归档并发数与临时磁盘配额。

### F-04（P1）：完全重复视频防护存在并发竞态

**证据**

- `backend/src/submissions/submissions.service.ts:469-482` 采用“查询已上传记录，再创建新上传”的 check-then-act 流程，且查询不包含正在上传的同哈希记录。
- `backend/src/database/entities/submission.entity.ts:33-70` 及初始迁移没有 checksum 唯一/排他约束。
- `backend/src/ai-quality/ai-quality-analysis.service.ts:328-344` 的二次精确重复检测只检查已有终态质量结果。

两个相同文件同时创建上传时都可能通过前置检查；如果两条 AI 任务也并发开始，它们都可能在对方成为终态前得到“非重复”，最终一起进入积分候选。

**修复建议**

按 checksum 获取 PostgreSQL advisory lock，或增加符合业务删除/重传规则的部分唯一索引，并把创建记录放进事务。精确重复判定应基于权威上传登记表，而不是等待另一条 AI 结果终态。补充并发创建和并发 AI 质检测试。

### F-05（P1）：运营和团队统计静默截断到 100 条

**证据**

- `web/src/features/admin/AdminDashboard.tsx:93-100` 只取第 1 页 100 条；只修正了 `totalSubmissions`，通过率、可交付资产和各流水线状态仍根据这 100 条计算。
- `web/src/features/team/TeamDashboard.tsx:61-64`、`TeamAnalyticsPage.tsx:68-85`、`MembersPage.tsx:107-126` 同样只取 100 条，再据此计算近 30 日、成员贡献、通过率和导出数据。
- `web/src/features/admin/AssetsPage.tsx:160-169` 只从 100 条中筛选最近资产。
- 后端已经返回 `pagination.total`，说明这里不是“真实数据少于 100 条”的可靠假设。

**影响**

数据量超过 100 后，页面仍显示“已连接后端数据”，但关键运营、团队和成员指标不再完整；这会影响运营判断和积分核对。

**修复建议**

把汇总、趋势、场景和成员贡献移到后端聚合 API，所有查询带明确时间范围和角色范围。短期方案可遍历全部分页，但不宜长期把全量明细拉到浏览器计算。测试数据至少覆盖 101 条和多页排序。

### F-06（P2）：MinIO 外部副作用与数据库事务缺少恢复协议

**证据**

- `backend/src/submissions/submissions.service.ts:651-695` 先完成 MinIO multipart，再写数据库和 outbox。MinIO 已完成而数据库事务失败时，记录仍是 uploading；重试完成 multipart 可能得到 `NoSuchUpload`。
- `backend/src/submissions/submissions.service.ts:1393-1476` 和 `1708-1795` 在数据库事务尚未提交时逐个删除 MinIO 对象。进程中断、部分删除失败或数据库提交失败时，MinIO 与数据库会暂时或长期不一致。

**修复建议**

把操作建模为可恢复状态（如 `completing`、`delete_pending`、`deleting`），外部操作全部幂等，完成后用条件更新落终态；增加周期性 reconciliation。multipart 完成重试时先 `headObject` 校验对象是否已经存在且大小/哈希正确。删除任务应记录每个 key 的进度或通过专用对象治理 Worker 执行。

### F-07（P2）：CSV 公式注入

**证据**

- `backend/src/audit/audit.service.ts:44-48`
- `backend/src/submissions/submissions.service.ts:109-113`
- `backend/src/points/point-cycles.service.ts:104-108`
- `backend/src/delivery/delivery-packages.service.ts:140-173`

这些 `csvCell` 只处理逗号、引号和换行，没有中和以 `=`, `+`, `-`, `@` 开头的单元格。文件名、显示名、团队名、交付包名和审计摘要中包含用户可控内容；导出后在 Excel 等软件中打开可能被当作公式。

**修复建议**

统一使用一个 CSV 库和安全单元格函数；对潜在公式前缀添加单引号或制表保护，并为 `=HYPERLINK(...)`、`+SUM(...)`、`@...` 等输入增加测试。所有 CSV 响应可加 UTF-8 BOM 以改善中文兼容性，但 BOM 不能替代公式防护。

### F-08（P2）：限流无法在真实多进程部署中提供稳定保护

**证据**

- `backend/src/security/rate-limit.service.ts:23-64` 使用进程内 `Map`，进程重启即清空，多实例之间不共享。
- `backend/src/security/login-rate-limit.guard.ts:15-18` 无条件信任客户端提供的 `X-Forwarded-For`。
- 项目已经部署 Redis，但业务代码没有使用 Redis；敏感操作限流也同样基于单进程内存。

账号自身的 5 次失败锁定能降低暴力破解风险，但攻击者仍可伪造 XFF 绕过 IP 维度，且可以用已知用户名触发账号锁定型拒绝服务。多 API 实例会把限额按实例数放大。

**修复建议**

使用 Redis 原子计数/滑动窗口；只在明确配置可信反向代理后使用 Express 的 `request.ip`，不要直接读取任意 XFF。登录建议同时设置 IP 全局、IP+用户名和账号维度，并对账号锁定策略加入渐进延迟与告警。

### F-09（P2）：所有登录页面服务端渲染时加载全量提交

**证据**

- `web/app/[[...slug]]/page.tsx:38-43` 每次登录后的页面渲染都调用 `listBackendSubmissions`，无论当前页面是否需要提交数据。
- `web/src/submissions/server/submissionBackendClient.ts:10-24` 请求 `/submissions` 时没有分页参数。
- `backend/src/submissions/submissions.service.ts:715-728` 只有调用方显式传 page/pageSize 才分页；否则返回当前角色可见的全部记录。
- 审计和提交 CSV 导出也直接 `getMany()`，没有导出条数上限或异步化。

**影响**

管理员每打开任意后台页面都会查询、序列化并水合全平台全部提交，数据增长后会显著增加 PostgreSQL 查询时间、SSR 内存、网络响应和浏览器内存；也抵消了页面内已经实现的分页。

**修复建议**

根页面只加载会话和必要身份信息，具体页面按需请求分页数据。删除 `DemoStoreProvider` 对全量 submission seed 的依赖。大型 CSV 改为游标流式导出或异步导出任务，并设置角色、时间范围和最大行数。

### F-10（P2）：CI 没有执行已经存在且当前失败的 lint

**证据**

- `web/package.json` 定义了 `pnpm lint`。
- `.github/workflows/ci.yml:89-100` 只执行 typecheck、test、build 和 render smoke，没有执行 lint。
- 本次实际运行 `pnpm lint` 得到 **22 个错误、3 个警告**。错误包括 effect 内同步 setState、hook 依赖缺失、声明前访问函数、render 中调用 `Date.now()` 及测试中的 `no-this-alias`。

因此当前 PR 即使 CI 全绿，仍不满足仓库自身的 lint 规则。

**修复建议**

先修复现有 lint，再把 `pnpm lint` 加入 Web CI，避免用全局 disable 掩盖问题。对于 `react-hooks/set-state-in-effect`，优先重构派生状态和请求状态，而不是逐行忽略规则。

### F-11（P2）：同一 PostgreSQL 事务连接上并发查询

**证据**

- `backend/src/submissions/submissions.service.ts:1808-1816` 在同一个 `EntityManager`/事务连接上用 `Promise.all` 并发执行三个 count。
- 完整后端测试虽然通过，但运行时出现 pg 警告：`Calling client.query() when the client is already executing a query is deprecated and will be removed in pg@9.0`。

**修复建议**

将三个 count 合并为一条 SQL，或在同一事务中顺序执行。加入 pg 9 兼容性准备项，避免未来升级后从警告变成运行时错误。

## 6. 做得较好的部分

- 全局 DTO whitelist、transform 和非白名单字段拒绝已启用。
- Session token 使用高熵随机值，并只在数据库保存 SHA-256 摘要；Cookie 设置了 HttpOnly、SameSite 和可配置 Secure。
- 密码使用 Argon2id，未知用户名也执行 dummy hash，降低用户名枚举的时序差异。
- 账号、团队、提交、积分和交付均有服务端权限策略，重要身份变更会撤销旧 Session。
- 积分周期和人工复核使用行锁控制关键并发，并保留调整流水与审计。
- 上传对象做大小校验，媒体 Worker 再做 SHA-256 和媒体元数据校验。
- Outbox、RabbitMQ confirm、重试队列、Worker 心跳和任务超时回收已经形成较好的可靠性基础。
- 测试覆盖了多数主路径、权限边界、数据库迁移、上传、AI、积分和交付流程。

## 7. 建议修复顺序

### 第一阶段：保证业务结果正确

1. 修复 F-01，统一规则引擎和规则快照语义。
2. 修复 F-04，建立 checksum 级数据库并发约束。
3. 修复 F-05，新增后端聚合指标 API，消除 100 条截断。

## 8. 其他低优先级观察

- `SESSION_SECRET` 被强制校验但当前 Session 实现并不使用它；容易让运维误以为它承担了 token 签名职责。
- Redis 和 Qdrant 当前没有业务调用，但 Compose 把它们设为 API 启动健康依赖，增加了无实际收益的故障面。
- 后端运行镜像没有切换到非 root 用户；正式部署建议创建专用 UID、只读根文件系统，并给归档临时目录单独限额。
- 前端保留大量 demo fallback。虽然页面通常会标记“演示数据”，但生产构建最好通过配置彻底关闭可操作 demo，接口失败时明确展示不可用状态，避免运营人员把演示结果当成真实结果。
