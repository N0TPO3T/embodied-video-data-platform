# 具身视频数据平台生产化产品设计

- 日期：2026-08-05
- 状态：产品方案已确认，待书面审阅
- 适用范围：桌面端 Web 第一阶段生产版本

## 1. 设计结论

本项目将在现有 Web 产品原型的基础上，建设可真实运营的具身视频数据平台。现有 React / TypeScript 前端继续使用；账号、视频、AI 评估、积分和统计等业务能力迁移到独立后端。后端采用模块化单体业务服务，并将耗时的视频处理和 AI 任务放入独立 Worker，通过队列异步执行。

产品聚焦三个核心闭环：

1. 数采人员稳定上传视频并查看个人结果。
2. 平台异步完成媒体检测与 AI 质量评估。
3. 团长管理本团队数采人员并监控产量、时长、质量和积分。

管理员负责全平台账号与团队管理、AI 异常任务处理和人工质量修正。平台只记录积分，不提供钱包、支付、提现或线上结算。团长根据平台导出的贡献明细在线下完成结算。

## 2. 产品目标

### 2.1 第一阶段目标

- 支持 20–100 名数采人员稳定使用。
- 支持每日不超过 500 条视频的常规处理量。
- 主要支持 3–5 分钟视频，同时正确处理少量 10 分钟以上视频。
- 批量选择的视频按单条任务独立上传、处理和重试。
- 数采人员、团长和管理员使用同一个账号密码登录入口。
- AI 结果、人工修正、积分变动和关键账号操作均可追溯。
- 个人、团队和平台统计均可从业务明细重新计算。

### 2.2 后续扩展目标

架构应能通过增加 API 实例、Worker 并发、队列容量和数据库资源，逐步扩展到 100–500 名乃至 1000 名以上数采人员。第一阶段不为远期规模提前引入微服务、Kubernetes 或多地域容灾。

## 3. 明确不在范围内的内容

第一阶段及本次总体建设方案不包含：

- 移动端网页、小程序或原生 App。
- 钱包、余额、支付、提现、发票和线上金额结算。
- 客服消息、工单、用户间聊天或站内私信。
- 团长或数采人员人工修改 AI 质量结果。
- 面向用户的视频删除功能。
- 自动化财务核算和打款。

平台仍保留必要的系统状态提示，例如上传失败、处理异常、评估完成和账号停用提示；这些提示不构成客服或聊天系统。

## 4. 角色与权限

### 4.1 数采人员

数采人员只能访问自己的数据，可以：

- 查看个人首页：上传数量、总时长、平均分、高分时长和积分。
- 批量选择并上传视频。
- 查看每条视频的上传与处理状态。
- 查看自己的视频、AI 分项结果、最终结果和积分。
- 查看采集规范。

数采人员不能查看其他成员数据，不能修改 AI 结果、积分、账号角色或团队关系。

### 4.2 团长

团长只能访问本团队数据，可以：

- 查看团队整体指标和趋势。
- 创建本团队数采人员账号。
- 修改本团队数采人员的显示名称。
- 重置本团队数采人员密码。
- 启用或停用本团队数采人员账号。
- 查看成员详情、成员视频和 AI 结果。
- 导出本团队贡献明细 CSV，用于线下结算。

团长不能：

- 删除账号。
- 修改角色或转移团队。
- 创建团长或管理员。
- 访问其他团队。
- 修改 AI 结果、质量规则或积分规则。

### 4.3 管理员

管理员拥有全平台运营权限，可以：

- 创建和管理管理员、团长及数采人员账号。
- 创建、调整和停用团队。
- 查看全量视频、AI 任务、积分和统计。
- 重试异常处理任务。
- 人工修正最终质量结果。
- 管理质量与积分规则版本。
- 查看关键操作审计日志。

人工修正必须填写原因，并永久保留修改人、修改时间、修改前数据、修改后数据和对应规则版本。AI 原始结果不可覆盖。

## 5. 页面与工作台

### 5.1 统一登录

所有角色共用用户名和密码登录页。服务端根据角色和团队关系返回权限，前端据此进入相应工作台。页面隐藏不作为权限依据；每个服务端接口必须再次校验角色和数据范围。

现有账号和团队关系应迁移到新后端。现有密码不要求用户修改：若旧密码摘要算法与新系统不同，新后端先兼容旧摘要，在用户成功登录后透明升级为新的密码摘要。明文密码不得写入代码仓库、日志或设计文档。

### 5.2 数采工作台

- 个人首页。
- 上传视频。
- 我的视频。
- 视频详情。
- 采集规范。
- 个人账号与退出登录。

### 5.3 团队管理台

- 团队首页。
- 成员管理。
- 成员详情。
- 团队视频。
- 数据导出。
- 团长个人账号与退出登录。

### 5.4 平台管理台

- 运营总览。
- 账号与团队管理。
- 全量视频。
- AI 任务中心。
- 质量复核。
- 质量与积分规则。
- 审计日志和系统设置。

## 6. 统计口径

所有时间口径默认使用 `Asia/Shanghai`，数据库中的时间以 UTC 保存。

- 上传数量：文件上传完成并成功登记的视频数量。
- 总时长：通过媒体基础检测的视频原始时长总和。
- 平均分：已完成质量评估视频的最终总分算术平均值。
- 高分时长：最终总分达到当前结果所绑定规则中“高分阈值”的视频有效时长总和。
- 积分：`有效时长（分钟） × 质量系数`。

积分计算保留原始有效秒数、换算后的有效分钟、质量系数、规则版本和计算结果。展示值保留两位小数，计算过程使用高精度十进制，避免累计浮点误差。

新规则只作用于规则生效后创建的评估结果，不自动改写历史结果。管理员明确发起重新评估或人工修正时，系统才使用指定的新规则生成新结果，并以积分冲正和新增记录体现变化。

AI 评估维度、阈值、质量系数和有效时长识别细则不在本文中定义。它们将在 AI 阶段开始前形成独立设计；本文固定规则版本、结果追溯、人工修正和积分接口，避免评估细则变化影响总体架构。

## 7. 总体架构

### 7.1 架构选择

采用“保留现有 Web 前端 + 独立后端”的方案：

- 前端：保留现有 React / TypeScript 页面与交互，逐步将模拟业务数据替换为真实 API。
- API：Python FastAPI 模块化单体服务。
- 数据库：PostgreSQL。
- 数据访问与迁移：SQLAlchemy + Alembic。
- 对象存储：兼容 S3 API 的私有对象存储。
- 队列：Redis。
- 异步任务：Celery Worker。
- 媒体处理：Python 调用 FFmpeg / FFprobe。
- AI：通过稳定的评估适配器调用选定模型或外部提供方。
- 本地开发：Docker Compose 运行后端依赖。
- 生产环境：容器化 API 与 Worker，使用托管 PostgreSQL、Redis 和对象存储。

第一阶段不拆分多个业务微服务。账号与团队、上传与视频、AI 编排、质量结果、积分和统计作为独立业务模块存在于同一 API 工程中，通过明确的内部接口协作。API 和 Worker 可独立横向扩容。

### 7.2 系统边界

```text
桌面 Web
  │
  ├── 业务 API ── PostgreSQL
  │      │
  │      ├── 签发临时上传凭证
  │      └── 创建异步任务 ── Redis 队列
  │
  └── 分片直传 ── 私有对象存储

Redis 队列
  ├── 媒体 Worker：FFprobe / FFmpeg
  ├── AI Worker：模型适配器
  └── 统计 Worker：积分与汇总
```

视频文件不经过 API 服务中转。API 只负责创建上传会话、签发短时凭证、确认上传完成和登记文件元数据。

## 8. 后端模块

### 8.1 身份与团队模块

负责：

- 用户名密码认证和可撤销会话。
- 角色、团队归属和账号状态。
- 团长与管理员的账号管理边界。
- 登录失败限流、会话失效和密码摘要升级。

### 8.2 上传与视频模块

负责：

- 创建单条上传任务。
- 签发分片上传凭证。
- 确认分片与文件完成。
- 记录对象存储键、校验值、文件大小和上传者。
- 维护视频处理状态。
- 提供个人、团队和管理员的视频查询。

一次批量选择会为每个文件创建独立上传任务。任一文件失败不会回滚或阻塞其他文件。

### 8.3 媒体处理模块

负责：

- 提取时长、分辨率、帧率、编码和容器格式。
- 验证文件是否可读取、可解码。
- 生成播放器需要的基础元数据。
- 将合法视频送入 AI 队列。
- 将损坏视频标记为媒体检测不通过并记录明确原因。

### 8.4 AI 编排与质量模块

负责：

- 创建评估任务并记录所用模型版本和规则版本。
- 管理排队、执行、超时、自动重试和最终失败。
- 保存分项结果、原始总分、问题项和有效时长。
- 向前端提供统一结果结构。
- 支持管理员人工修正并保留完整审计链路。

AI 提供方封装在适配器之后。更换模型或从外部 API 切换到自托管模型时，不改变视频、积分和统计模块的接口。

### 8.5 积分模块

负责：

- 根据最终有效时长、质量系数和规则版本计算积分。
- 通过不可覆盖的积分明细记录初始记分、冲正和修正后记分。
- 保证重复任务或重复通知不会重复记分。
- 提供个人、团队和平台积分查询。

积分是贡献记录，不是货币余额。

### 8.6 统计模块

负责：

- 生成个人、团队和平台日汇总。
- 计算数量、总时长、平均分、高分时长和积分。
- 在评估完成或人工修正后增量更新统计。
- 定时核对明细与汇总，并在发现差异时重建统计。

统计快照用于加速查询，不是唯一事实来源。

### 8.7 审计模块

统一记录：

- 账号创建、启停、密码重置、角色和团队变更。
- AI 任务人工重试。
- 质量结果人工修正。
- 规则发布和启停。
- 管理员执行的归档或数据修复操作。

## 9. 视频生命周期

### 9.1 正常流程

```text
准备上传
  → 上传中
  → 已上传
  → 媒体检测中
  → AI 排队中
  → AI 评估中
  → 已完成
```

处理步骤：

1. 网页检查文件扩展名、大小和浏览器可读取性。
2. 后端为每条视频创建独立上传会话。
3. 浏览器将分片直接上传至对象存储。
4. 上传完成后，后端验证对象并创建媒体检测任务。
5. 媒体 Worker 提取参数并验证可解码性。
6. 合法视频进入 AI 队列。
7. AI Worker 生成原始质量结果。
8. 积分模块计算初始积分。
9. 统计模块更新个人、团队和平台汇总。

### 9.2 异常状态

- 上传暂停：保留已完成分片，用户可继续上传。
- 上传失败：只重试当前文件。
- 媒体检测不通过：标记为“不通过”，保留原因，不进入 AI。
- AI 临时失败：后台指数退避自动重试。
- AI 多次失败：标记为“处理异常”，进入管理员异常列表。
- Worker 意外退出：任务可被重新领取，不重复产生结果或积分。

长视频和短视频使用同一状态机，但独立排队。长视频只增加自身处理时间，不阻塞同一批次中的其他任务。

### 9.3 人工修正

人工修正作为 AI 原始结果之后的独立版本：

```text
AI 原始结果（不可改）
  → 管理员填写修正值和原因
  → 生成最终结果新版本
  → 冲正旧积分并生成新积分
  → 更新统计快照
```

团长和数采人员始终只读。

## 10. 核心数据模型

主要实体如下：

- `teams`：团队及状态。
- `users`：用户名、显示名称、角色、团队、账号状态和密码摘要。
- `sessions`：可撤销登录会话。
- `upload_sessions`：分片上传会话、对象键和完成状态。
- `videos`：上传者、团队、文件信息、处理状态和最终结果引用。
- `media_metadata`：时长、分辨率、帧率、编码和检测结果。
- `processing_jobs`：任务类型、尝试次数、超时、错误和幂等键。
- `ai_evaluations`：模型版本、规则版本、分项结果、原始分和有效时长。
- `quality_corrections`：修正前后值、原因、管理员和时间。
- `rule_versions`：质量阈值、系数、状态和生效时间。
- `point_ledger`：初始记分、冲正、重新记分及来源结果。
- `daily_statistics`：用户、团队和平台的日汇总快照。
- `audit_logs`：关键操作的主体、对象、前后数据和请求信息。

业务明细采用软状态变更，不允许普通用户物理删除。第一阶段不提供视频删除界面；如确需释放存储，由管理员执行有审计的归档流程。未形成正式保留策略前，不自动物理删除生产视频。

## 11. API 设计原则

- API 统一使用版本前缀，例如 `/api/v1`。
- 前端只依赖公开响应模型，不依赖数据库字段。
- 列表接口统一支持分页、时间范围、状态和角色允许范围内的筛选。
- 写操作支持幂等键；上传完成、AI 完成和积分计算可安全重复调用。
- 错误响应包含稳定错误码和面向用户的简短说明。
- 视频播放和下载使用短时签名地址。
- AI、对象存储和队列通过内部适配器隔离具体供应商。

主要 API 域：

- `/auth`
- `/users`
- `/teams`
- `/uploads`
- `/videos`
- `/evaluations`
- `/corrections`
- `/points`
- `/statistics`
- `/rules`
- `/audit-logs`

## 12. 安全设计

- 新密码使用 Argon2id 摘要。
- 登录会话通过 `HttpOnly`、`Secure`、`SameSite` Cookie 传输，并可由服务端撤销。
- 修改密码、停用账号或修改关键权限后，使相关旧会话失效。
- 所有接口在服务端执行角色和团队范围校验。
- 登录、密码重置、上传凭证和管理接口设置频率限制。
- 同源写请求使用 CSRF 防护。
- 对象存储默认私有，只通过短时签名地址访问。
- 日志不记录密码、会话令牌、上传密钥或完整签名地址。
- 管理员修正、规则变更和账号权限变更均记录审计日志。
- 生产密钥由部署环境或密钥服务提供，不写入仓库。

## 13. 数据一致性与恢复

- 每个异步任务使用稳定幂等键，重复投递不会重复落结果。
- AI 结果、人工修正和积分均以追加版本或明细记录保存。
- 数据库事务保证“最终结果发布”和“积分变动创建”原子完成。
- 统计更新允许短暂延迟，但必须能从明细重建。
- 定时核对任务检查已完成视频、积分明细和统计快照的对应关系。
- PostgreSQL 执行自动备份并定期验证恢复。
- 对象存储启用版本保护或等价的误删保护能力。
- 队列积压、任务失败率、处理耗时和存储错误必须可监控并告警。

## 14. 测试策略

### 14.1 单元测试

重点覆盖：

- 角色与团队权限。
- 视频状态机。
- 积分公式和小数精度。
- 规则版本生效边界。
- AI 重试与幂等。
- 人工修正、冲正和重算。
- 统计口径。

### 14.2 集成测试

验证：

- API 与 PostgreSQL。
- 分片上传、断点续传和对象存储确认。
- Redis 队列与 Worker。
- 媒体检测与损坏文件。
- AI 适配器超时、重试和失败隔离。
- 结果完成后的积分与统计更新。

### 14.3 端到端测试

分别模拟：

- 数采人员登录、上传、续传、查看结果。
- 团长创建成员、停用成员、查看团队数据和导出 CSV。
- 管理员查看异常、重试任务、修正结果和查看审计日志。
- 越权访问其他用户或其他团队被服务端拒绝。

### 14.4 容量与故障演练

以首期每日 500 条视频为常规基线，覆盖上传峰值、10 分钟以上视频和 AI 队列积压。演练 API 重启、Worker 重启、Redis 短暂不可用、对象存储超时和 AI 提供方超时，验证任务恢复、幂等和告警。

## 15. 现有原型迁移策略

- 保留现有 Web 前端的视觉结构和已验证交互。
- 将浏览器内模拟业务数据逐页替换为真实 API。
- 新后端成为账号、团队和全部业务数据的唯一事实来源。
- 迁移现有真实账号、团队关系和账号状态。
- 通过兼容旧摘要并在登录后透明升级的方式保留现有密码。
- 原型中的演示视频、模拟 AI 结果、模拟积分、结算和提现数据不迁入生产数据库。
- 删除产品导航中的客服、钱包、结算和提现相关入口。
- 前后端切换按角色和页面分批进行，不要求一次性替换全部页面。

## 16. 分阶段交付

本文是覆盖完整产品的总体设计，不应被展开成一个同时实施全部模块的超大开发任务。五个阶段分别形成独立实施计划、独立验收和独立上线检查；上一阶段通过验收后再进入下一阶段。这样既保留统一架构，也让每轮建设保持可验证和可回退。

### 阶段 1：工程基础与账号体系

交付：

- 独立后端、数据库迁移、配置与部署骨架。
- 登录、三类角色、团队归属和账号状态。
- 管理员与团长的账号管理权限。
- 审计与基础监控。

验收：三类账号均可登录并严格访问自己的数据范围；账号变更可追溯。

### 阶段 2：真实视频上传闭环

交付：

- 对象存储直传、分片和断点续传。
- 批量选择、单条进度和失败重试。
- 媒体参数解析和损坏检测。
- 个人、团队和管理员视频列表与详情。

验收：3–5 分钟和 10 分钟以上视频均可独立上传、续传、检测和查询。完成本阶段后，可开始小范围真实上传试用。

### 阶段 3：AI 质量评估与积分

交付：

- 经单独确认的 AI 评估与积分规则设计。
- 异步评估队列、进度、超时与重试。
- 原始结果、有效时长、最终结果和积分。
- 管理员人工修正、规则版本和积分变动记录。

验收：每条合法视频都有可解释、可追溯的结果；人工修正后积分准确重算。

### 阶段 4：团队运营与统计看板

交付：

- 个人、团队和平台指标与趋势。
- 成员详情和视频下钻。
- 筛选、排行与异常定位。
- 团队贡献明细 CSV 导出。

验收：统计可从明细重建，口径一致，导出数据可支持线下核算。完成本阶段后，核心产品闭环成立。

### 阶段 5：生产化与正式上线

交付：

- 全流程、权限、容量和故障恢复验证。
- 日志、告警、备份、恢复和数据核对任务。
- 原型数据清理与真实用户分批开放。

验收：真实用户试运行稳定，故障可定位可恢复，关键数据具备备份和核对机制。

## 17. 总体验收标准

产品达到生产版本要求时，应满足：

1. 数采人员能稳定上传多条真实视频，单条失败不影响其他视频。
2. 长视频不会阻塞同批次短视频。
3. 每条合法视频可完成媒体检测、AI 评估、积分和统计更新。
4. 团长只能管理和查看本团队数采人员。
5. 只有管理员能修正质量结果，且原始结果与修正记录完整保留。
6. 积分可根据结果追溯，不包含任何线上资金能力。
7. 个人、团队和平台指标采用统一口径，可从明细重建。
8. 上传、AI 和 Worker 异常可重试、可恢复且不会重复记分。
9. 关键账号、规则和质量操作均有审计记录。
10. 客服、聊天、钱包、结算、提现和移动端功能未进入产品范围。

## 18. 后续设计入口

本文通过书面审阅后，下一步只编制“阶段 1：工程基础与账号体系”的详细实施计划。阶段 1 通过验收后，再依次为后续阶段编制各自的详细实施计划。

实施进入阶段 3 前，需要单独完成 AI 视频质量评估细则设计，确定评估维度、取样方式、阈值、有效时长判定、质量系数和模型验收集；该设计不得改变本文已经确认的角色权限、结果版本、积分明细和统计接口边界。
