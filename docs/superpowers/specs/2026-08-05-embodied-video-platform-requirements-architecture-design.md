# 具身智能视频数据平台
## 整体需求清单与技术实现方案

- 文档版本：v1.0（技术沟通版）
- 编写日期：2026-08-05
- 适用对象：产品负责人、技术负责人、Web/小程序开发、后端开发、AI/数据开发、测试与运维
- 规划口径：约 1000 名总用户，Web 管理端 + 微信小程序成员端
- 文档用途：需求评审、技术选型、接口和数据模型讨论、开发拆分、试运行验收

> 本文把“已经确认的业务规则”“建议默认值”和“需要技术老师拍板的候选项”分开标记。没有确认的参数不得由开发人员直接写死。

# 0. 结论先行

一期不应建设成大而全的数据交易平台，而应优先打通一条可运营、可追溯、可结算的具身视频数据生产闭环：

账号与团队 → 小程序/Web 上传视频 → 媒体处理 → AI 标签与质检 → 结算前人工调整 → 数据资产入库 → 日结算与余额 → 人工提现

推荐总体方案：

1. 延续现有 React、TypeScript、Cloudflare Workers/Sites 和 D1 工程，不推倒重做。
2. D1 只保存用户、提交、状态、评分摘要、价格和资金流水等结构化数据。
3. R2 保存原视频、预览、缩略图、证据帧、完整 AI 输出和交付包。
4. Cloudflare Queues 只传任务 ID 和对象键，不传视频或完整 AI 结果。
5. FFmpeg、模型调用和 GPU 推理放到独立 Worker 容器，通过队列异步处理。
6. 微信小程序一期只提供成员端核心能力，优先采用 Taro + React，共用 API、类型和业务规则，不承诺直接复用 Web DOM 组件。
7. 以 1000 名总用户设计：峰值在线 60-120 人、同时上传 10-30 个、业务接口短时峰值 50-100 RPS、AI 并发 8-16 个。
8. D1 可以支撑一期试运行，但必须保持“瘦数据”。如果日均长期超过 500-1000 个视频、复杂报表明显增加，或预计一年内结构化数据接近 6 GB，应提前迁移托管 PostgreSQL。
9. 一期开发前先完成“大视频小程序真机上传”和“真实 AI 输出协议”两个技术验证，否则排期容易失真。

- IMU、6DoF、深度、标定和专用采集 App。
- 自建模型训练平台。
- Kubernetes 和过早微服务化。

# 3. 用户、组织与权限

## 3.1 角色定义

| 角色 | 主要职责 | 数据范围 |
|---|---|---|
| 普通成员 | 上传视频、查看质检、查看收入、申请提现 | 仅本人 |
| 团长 | 查看本团成员和数据、调整未结算质检结果 | 仅本团 |
| 平台管理员 | 用户团队、规则、全平台数据、结算、提现和审计 | 全平台 |
| 采购商（二期） | 查看被授权目录、申请样本和下载交付包 | 授权范围 |

一期不设置独立质检员、客服、运营和财务角色。若后续需要，应采用权限点扩展，不新增重复后台。

## 3.2 权限实现原则

- 前端隐藏无权限页面、菜单和按钮。
- 后端每个接口再次校验角色和数据范围。
- 团长查询必须附加团队条件，普通成员查询必须附加本人条件。
- 文件预览和下载使用短期签名地址，不能返回永久公开链接。
- 价格、质检调整、结算、提现、用户状态和删除必须写审计日志。
- 移除团队成员不能删除其历史视频、质检和资金关系。

| ID | 需求点 | 实现与验收 |
|---|---|---|
| UP-01 | 文件范围 | 一期只接受 MOV、MP4；后端检查真实容器而非只看扩展名 |
| UP-02 | 上传批次 | 一次多选形成一个上传批次，每个视频形成独立提交 |

| UP-04 | 分片上传 | 大文件使用 multipart；支持暂停、继续、失败分片重试和恢复 |
| UP-05 | 幂等完成 | 同一上传会话重复提交完成请求不能创建两份数据提交 |

- Web 分片：16-32 MiB，每文件并发 4-6 片。
- 小程序分片：8-16 MiB，每文件并发 2-3 片。
- R2 multipart 除最后一片外必须保持相同大小。
- 上传会话保存 `upload_id`、对象键、分片号、ETag、文件大小和过期时间。
- 小程序一期按“可恢复上传”验收，不把切到后台后持续上传作为默认承诺。

## 4.6 AI 任务、标签与质检

| ID | 需求点 | 实现与验收 |
|---|---|---|
| AI-01 | 单视频独立任务 | 单个文件完成校验后立即入队，不等待同批其他文件 |
| AI-02 | 任务状态 | 排队、处理中、重试中、成功、系统失败分别保存 |
| AI-03 | 处理阶段 | 媒体预检、画质、内容标签、动作片段、无效区间、重复候选和综合评分 |
| AI-04 | 模型适配层 | 第三方 API、自建模型和规则检测统一输出标准协议 |
| AI-05 | 模型与规则版本 | 每次结果记录模型、提示词/参数和规则版本 |
| AI-06 | 原始结果不可覆盖 | 重跑产生新的 ModelRun/QCRun，历史结果仍可查 |
| AI-07 | 证据 | 问题保存原因码、严重度、扣分、时间范围、证据帧和置信度 |
| AI-08 | 标签 | 保存场景、动作、对象、工具、第一视角和任务摘要 |
| AI-09 | 失败重试 | 网络、模型、Worker 错误自动重试；达到上限进入死信/人工重跑 |
| AI-10 | 失败分离 | 系统处理失败不能记为成员视频质量失败 |
| AI-11 | 重复检测 | 文件哈希拦完全重复，视觉近似一期只生成候选，不自动扣款 |

质检分层：

1. L0 文件合法性：容器、损坏、截断和媒体解析。
2. L1 画面质量：模糊、曝光、抖动、黑屏、遮挡、静止和手部可见。
3. L2 内容理解：第一视角、场景、对象、工具、动作片段和动作完整性。
4. L3 重复与覆盖：完全重复、视觉近似和场景动作库存覆盖。
5. L4 综合结果：分数、硬淘汰项、无效区间、改进建议和是否可入库。

# 6. 核心状态机和业务规则

## 6.1 状态必须拆分

不能用一个 `status` 同时表达所有阶段。至少拆为：

- 上传：待上传 → 上传中 → 校验中 → 上传完成 / 上传失败。
- AI：待创建 → 排队中 → 处理中 → 重试中 → 成功 / 系统失败。
- 质量：未评分 → AI 通过/不通过 → 最终通过/不通过。
- 资产：未入库 → 候选 → 已入库 → 已下架/归档。
- 结算：未计价 → 待结算 → 处理中锁定 → 已入账/不计费关闭。
- 提现：待审核 → 已撤回/已驳回/待打款 → 已完成/打款失败。

## 6.2 端到端数据流

客户端申请上传会话
→ API 在 D1 建立会话并返回 R2 分片凭证
→ 客户端把视频分片直传 R2
→ API 校验分片并确认完成
→ D1 创建独立数据提交
→ Queues 写入任务 ID
→ 媒体/AI Worker 从 R2 读取视频
→ 派生文件和完整结果写回 R2
→ 评分摘要、状态和索引写入 D1
→ 管理员/团长在结算前调整
→ 日结算锁定结果并写钱包流水

## 6.3 幂等唯一键

建议至少设置：

- 上传完成：`upload_session_id` 唯一。
- 数据提交：`source_file_id` 唯一。
- AI 任务：`submission_id + pipeline_version + run_no` 唯一。
- 结算明细：`submission_id` 正常结算唯一。
- 钱包流水：`business_type + business_id + direction` 唯一。
- 日批次：`business_date` 唯一。
- 提现冻结和退回：`withdrawal_id + ledger_action` 唯一。

# 7. 推荐技术架构

## 7.1 推荐方案 A：Cloudflare 业务层 + 外部媒体/AI Worker

这是与现有代码最匹配、一期迁移成本最低的方案。

Web / Taro 微信小程序
→ Cloudflare Worker API
→ D1：账号、业务状态、评分摘要、价格、资金和审计
→ R2：原视频、预览、抽帧、完整 AI 输出和交付包
→ Queues：任务 ID、阶段和优先级
→ 外部 FFmpeg/AI Worker 容器：CPU/GPU 处理
→ 定时任务：结算、统计、超时回收和一致性检查

关键约束：

- Queues 消息只放小型 JSON，不放视频、图片或完整模型结果。
- 外部 Worker 使用 pull consumer 或安全任务 API 领取任务。
- Worker 先写 R2 完整产物，再以幂等接口提交 D1 摘要。
- D1 查询必须有索引和分页，公开统计使用快照。
- 日结算、钱包和提现使用批处理、唯一键和补偿保证一致性。

## 7.2 组件职责

| 组件 | 负责 | 不负责 |
|---|---|---|
| Web/小程序 | 页面、上传控制、状态展示、表单校验 | 资金最终校验、权限最终判断 |
| Worker API | 登录、权限、业务事务、签名、状态查询 | 转发视频、执行长时间 GPU 推理 |
| D1/数据库 | 结构化业务关系、索引、状态和账本 | 视频和大型原始 AI JSON |
| R2/对象存储 | 视频、图片、派生文件和结果文件 | 用户关系、余额和结算 |
| Queues | 解耦、重试、削峰和任务调度 | 长期保存业务事实 |
| 媒体/AI Worker | FFmpeg、模型调用、特征和结果生成 | 直接决定用户权限和资金入账 |

# 8. 技术候选项与老师确认点

## 8.1 云与数据库候选

| 方案 | 优点 | 风险/代价 | 建议 |
|---|---|---|---|
| A. D1 + R2 + Queues | 最大复用现有工程，运维少，一期上线快 | D1 单库 10 GB、单库串行；境内小程序网络需真机验证 | 一期推荐 |
| B. Workers + R2 + 托管 PostgreSQL | 查询和事务能力更强，容量扩展更从容 | 增加数据库连接、迁移和成本，需确认 Workers 连接方案 | 日均长期高于 500-1000 视频时优先 |
| C. 境内云一体化 | 小程序访问、域名和境内运维路径更直接 | 现有 Cloudflare 工程迁移量更大，运维组件更多 | 如果用户主要在中国大陆且上线资质要求明确 |

需要技术老师回答：

1. 正式用户主要位于中国大陆还是海外？
2. 是否已经有可用于小程序的备案域名和云账号？
3. 是否接受 D1 作为一期数据库，还是公司规范要求 PostgreSQL/MySQL？
4. 预计 12 个月的视频提交量和结构化数据增长是多少？

## 8.2 小程序候选

| 方案 | 优点 | 风险/代价 | 建议 |
|---|---|---|---|
| Taro + React | 与现有 React/TypeScript 思路一致，可复用类型、API 和部分业务逻辑 | Web 组件和 CSS 不能直接照搬，大视频能力仍需平台专项适配 | 推荐 |
| 微信原生 | 平台能力最直接，上传和审核问题定位更容易 | 两套 UI 工程，复用较少，开发维护成本更高 | 上传遇到框架限制时选 |
| uni-app | Vue 团队成熟、跨端生态丰富 | 与现有 React 工程复用较少 | 团队更熟悉 Vue 时选 |

小程序第一周必须完成技术验证：

- 原始视频选择后能否拿到满足需求的临时文件。
- 100 MB、500 MB、1 GB 样本的上传成功率和内存占用。
- iPhone/安卓、Wi-Fi/4G/弱网、前后台切换后的恢复。
- 分片上传到目标对象存储的域名、HTTPS、CORS 和签名流程。
- 隐私协议、权限说明和审核材料。

## 8.3 AI 方案候选

| 方案 | 优点 | 风险/代价 | 建议 |
|---|---|---|---|
| 第三方多模态 API | 接入快，适合验证标签和质检闭环 | 成本、时延、数据出境/授权、输出稳定性 | 用于试运行或辅助理解 |
| 自建开源模型服务 | 数据控制和批量成本可控 | GPU、模型效果、部署和维护成本高 | 有明确算法团队后采用 |
| 混合方案 | 确定性规则 + 开源检测 + 多模态 API，逐步替换 | 需要统一协议和结果融合 | 一期推荐 |

一期建议：

- L0 媒体合法性和基础指标使用 FFmpeg/确定性规则。
- L1 画质使用开源检测器和规则。
- L2 内容、动作和建议可以调用现有模型服务或多模态 API。
- L3 完全重复用哈希，近似重复先做轻量特征候选。
- 最终分由版本化规则引擎汇总，不让模型直接写钱包金额。

## 8.4 媒体 Worker 候选

| 方案 | 适用情况 | 建议 |
|---|---|---|
| 自管 Docker FFmpeg Worker | 有现成云主机，需可控、可调试 | 一期推荐 |
| 云厂商媒体处理服务 | 转码规模大，希望减少运维 | 作为备选，先核算费用和对象存储兼容 |
| 全部放 Serverless 函数 | 仅短任务和小文件 | 不建议承载长视频转码/GPU 推理 |

# 9. 1000 用户容量规划

以下是规划假设，不是业务承诺。上线前必须用 20-50 条真实视频重新测量平均大小、时长和处理耗时。

## 9.1 用户与并发

| 指标 | 规划值 | 设计含义 |
|---|---:|---|
| 总注册用户 | 1000 | 约 40-50 个团队 |
| 日活用户 | 100-300 | 10%-30% 日活假设 |
| 峰值在线 | 60-120 | 主要查看列表和状态 |
| 业务 API 常态 | 10-30 RPS | 不含视频字节流 |
| 业务 API 短时峰值 | 50-100 RPS | 登录、刷新和批量完成回调 |
| 同时上传 | 10-30 个文件 | 视频直传对象存储 |
| AI 并发 | 8-16 个任务 | 根据单视频耗时动态调节 |

业务 API 不承担视频流后，1000 名总用户不是主要压力；真正需要重点规划的是上传带宽、对象存储和 AI 处理队列。

## 9.2 视频与存储量级

按平均每个原视频 300 MB 估算：

| 场景 | 视频/日 | 原始/日 | 原始/月 | 加 30% 派生文件/月 | 90 天热存储 |
|---|---:|---:|---:|---:|---:|
| 试运行 | 100 | 30 GB | 0.9 TB | 1.17 TB | 约 3.5 TB |
| 基准 | 500 | 150 GB | 4.5 TB | 5.85 TB | 约 17.6 TB |
| 压力 | 1500 | 450 GB | 13.5 TB | 17.55 TB | 约 52.7 TB |

计算公式：

- 日原始量 = 日视频数 × 平均文件大小。
- 月原始量 = 日原始量 × 30。
- 总热存储 = 原始量 ×（1 + 派生比例）× 保留月数。

需要尽快确认：

- 平均视频时长和原始大小。
- 原始失败视频保留多久。
- 预览、抽帧和模型中间文件的派生比例。
- 已交付、未交付和失败数据的冷热分层规则。

## 9.3 数据库量级

数据库必须只保存“瘦元数据”：

- 每个视频的结构化记录、标签、问题和索引目标控制在约 10-20 KB。
- 500 视频/日约为 18.25 万条提交/年，业务数据约 1.8-3.7 GB/年，加入索引、审计和增长后按 3-6 GB/年预留。
- 1500 视频/日约为 54.75 万条提交/年，单 D1 很可能在一年内接近或超过 10 GB。
- 完整 AI JSON、密集帧结果、特征文件和证据图片必须放 R2，D1 只保存摘要和对象键。

D1 迁移触发线建议：

- 单库达到 6 GB。
- 日均稳定超过 500-1000 视频。
- 复杂运营报表频繁扫描大表。
- 高峰持续出现数据库 overloaded。
- 出现多事务、多租户隔离或 BI 直连需求。

## 9.4 AI 吞吐估算

理论吞吐：

每小时处理量 = AI 并发数 × 3600 ÷ 单视频平均处理秒数

例如平均每个视频 5 分钟：

- 8 并发约 96 个/小时。
- 12 并发约 144 个/小时。
- 16 并发约 192 个/小时。

如果日上传集中在 12 小时内，1500 个/日约需要 125 个/小时，因此 12-16 个并发是压力场景的起点。最终并发应根据 GPU 显存、模型限流、单视频时长和成本动态调整。

# 10. 数据存储设计

## 10.1 D1/关系数据库保存

- 用户、账号、会话、团队和成员历史。
- 上传批次、数据提交和文件元数据。
- AI 任务、阶段、尝试次数和错误摘要。
- 标签索引、质量摘要、问题索引和无效区间。
- 人工调整和审计。
- 资产状态和统计快照。
- 价格规则、结算批次、计价快照、钱包和提现。

## 10.2 R2/对象存储保存

- 原始视频。
- 低码率预览和缩略图。
- 质检抽帧和证据帧。
- 完整 AI 原始输入/输出 JSON。
- 视觉特征和可重建的中间结果。
- 二期交付包。

## 10.3 对象键建议

`env/{environment}/tenant/{platform}/submission/{submission_id}/{layer}/{version}/{filename}`

示例：

- `prod/platform/submission/SUB123/raw/v1/source.mp4`
- `prod/platform/submission/SUB123/preview/v1/preview.mp4`
- `prod/platform/submission/SUB123/evidence/run-2/frame-0012.jpg`
- `prod/platform/submission/SUB123/ai/run-2/result.json`

对象键不要包含用户名、手机号、收款账号等个人信息。

# 11. 核心数据对象

| 领域 | 核心对象 |
|---|---|
| 身份组织 | User、Session、Team、TeamMembership、RolePermission |
| 上传文件 | UploadBatch、UploadSession、DataSubmission、RawFile、DerivedFile、MediaMetadata |
| AI 质检 | ProcessingJob、ModelRun、LabelDefinition、VideoLabel、SegmentLabel、QualityResult、QualityIssue、InvalidInterval |
| 复核重复 | ManualReview、DuplicateCandidate |
| 资产统计 | DataAsset、AssetVersion、DistributionSnapshot、PublicSnapshot |
| 资金 | PriceRule、PricingRecord、SettlementBatch、WalletAccount、LedgerEntry、WithdrawalRequest |
| 运维审计 | AuditLog、ScheduledJobRun、WorkerHeartbeat、SystemAlert |

数据建模原则：

- AI 原始结果和人工最终结果分开。
- 当前汇总值可以缓存，但必须能追溯到不可变历史记录。
- 账本流水不可更新和删除，只能追加。
- 标签使用可配置表和多对多关系，不能写死为代码枚举。
- 所有大 JSON 和二进制对象通过 R2 键引用。

# 12. API 分组建议

| API 组 | 主要能力 |
|---|---|
| `/api/auth/*` | 登录、退出、会话、微信绑定 |
| `/api/admin/accounts/*` | 账号、角色、团队和密码管理 |
| `/api/teams/*` | 团队、成员、指标和成员历史 |
| `/api/uploads/*` | 创建会话、分片凭证、列出分片、完成和取消 |
| `/api/submissions/*` | 列表、详情、状态、预览地址和返工关联 |
| `/api/jobs/*` | AI 队列、重跑、阶段和错误 |
| `/api/quality/*` | AI 结果、证据、人工调整和重复候选 |
| `/api/assets/*` | 资产、分布、下架和公开快照 |
| `/api/rules/*` | 标签、质检、模型、价格和生效版本 |
| `/api/settlements/*` | 预览、生成、批次、明细和补跑 |
| `/api/wallet/*` | 余额、流水、提现申请和撤回 |

统一接口要求：

- JSON 字段和错误码有版本。
- 列表统一分页、排序和筛选。
- 写接口支持 `idempotency_key`。
- 返回 `trace_id`，便于用户反馈时定位。
- 小程序和 Web 共用接口，不为小程序复制一套业务服务。

# 13. AI Worker 输入输出协议

## 13.1 任务输入最小字段

- `job_id`
- `submission_id`
- `source_object_key`
- `pipeline_version`
- `requested_stages`
- `callback_token` 或 Worker 身份
- `trace_id`

队列消息不直接携带视频和完整规则。Worker 根据任务 ID 获取短期文件访问权限和当前版本配置。

## 13.2 结果输出最小字段

- 执行状态和阶段耗时。
- 媒体参数。
- 视频级标签和片段标签。
- 五项分数、总分和质量建议。
- 硬性淘汰项。
- 无效时间区间。
- 质量问题、证据帧和置信度。
- 重复候选及相似度。
- 模型、提示词/参数和规则版本。
- 完整结果对象键。

## 13.3 结果校验

- 服务端使用 JSON Schema/类型校验，不接受缺失关键字段的“成功”结果。
- 超范围分数、负时间、重叠非法区间和不存在的对象键必须拒绝。
- Worker 重复提交相同 run 的结果时幂等返回。
- 只有完整结果通过校验后，才能产生质量结论。

# 14. 安全、隐私与合规

一期至少落实：

- 原视频和派生文件默认私有。
- 短期签名上传、预览和下载。
- 服务端角色和数据范围校验。
- 密钥只放环境 Secret，不进入代码、日志或小程序包。
- 收款账号脱敏显示，提交提现时保存收款信息快照。
- 人脸、声音、地址、屏幕和定位等敏感内容的处理规则必须形成书面规范。
- 上传前展示数据使用授权和禁止内容说明。
- 管理员物理删除使用独立高风险流程并保留审计。
- 若调用第三方 AI，必须确认数据传输地区、保存策略和是否用于训练。

待法务/合规确认：

- 上传协议和数据授权主体。
- 人脸、声音和家庭场景数据是否允许采集。
- 原视频、失败视频和已交付数据的保留周期。
- 数据跨境或第三方模型调用限制。
- 用户申请删除时，账务和审计记录的保留边界。

# 15. 运行、监控、备份与发布

## 15.1 环境

- `dev`：本地/个人测试数据。
- `staging`：真实流程联调，不使用真实收款账户打款。
- `prod`：正式数据，独立 Secret、D1/R2/Queue 和 Worker。

## 15.2 监控指标

- API 请求量、错误率和 P95 延迟。
- 上传成功率、分片失败率和平均上传时长。
- 队列积压量和最老任务等待时间。
- AI 成功率、重试率、单阶段耗时和单视频成本。
- Worker 在线数、CPU/GPU/显存和心跳。
- 日结算成功率、异常明细和钱包对账差异。
- 对象存储缺失、孤儿对象和一致性检查结果。

## 15.3 告警起点

- API 5xx 连续 5 分钟高于 2%。
- 上传完成失败连续 5 分钟高于 5%。
- 最老 AI 任务等待超过 30 分钟。
- Worker 全部离线超过 3 分钟。
- 日结算存在未处理失败明细。
- 钱包账本汇总与余额不一致。

阈值在试运行后调整。

## 15.4 备份恢复

- D1/数据库开启自动备份或时间点恢复。
- 关键配置、规则版本和迁移文件进入版本控制。
- 原始层和资产层设置合理生命周期与误删保护。
- 每季度至少演练一次：恢复数据库、重新绑定对象、补跑任务和核对余额。

- 真实 AI 接口输出与预期明显不一致。
- 云环境或对象存储接入异常。

二期建议项合计 12.5 人天。上述数字是“复用现有代码 + 已有 AI 服务接口 + 单名熟练全栈开发者使用 AI 辅助”的目标口径，不包含模型训练、云资源费用、第三方 API、短信、支付通道、硬件和财税咨询。

## 16.1 推荐迭代

1. 技术验证：小程序大视频上传、R2 multipart、外部 Worker 拉队列、真实 AI 协议。
2. M0-M1：业务表、API 适配、权限和团队。
3. M2：Web/小程序共用上传后端、媒体解析。
4. M3：队列、AI、结果落库、异常恢复。
5. M4-M5：人工调整、资产、结算、钱包和提现。
6. M7：在稳定 API 上完成小程序页面与真机发布。
7. M6：端到端、压力、恢复演练和试运行修复。

小程序页面可以与后端并行搭骨架，但大视频上传和登录绑定必须优先验证。

# 17. 一期验收标准

## 17.1 功能闭环

- 成员能通过 Web 和小程序登录并上传 MOV/MP4。
- 单个视频完成校验后立即进入独立 AI 队列。
- 系统生成媒体参数、标签、质量分、问题证据和有效时长。
- 系统错误不产生质量失败。
- 管理员和团长可按权限调整未结算结果。
- 每日结算不会重复入账。
- 成员可查看余额并申请提现，管理员完成线下打款状态管理。
- 已结算通过的数据进入资产和公开快照。

## 17.2 稳定与容量

- 20-50 条真实样本完成端到端回归。
- Web 和小程序在网络中断后可恢复上传。
- 一个文件失败不影响同批其他文件。
- 500 视频/日基准压测下，队列在约定时间内清空。
- API 短时 100 RPS 不出现持续错误或明显积压。
- Worker 宕机后任务可重新领取。

## 17.3 权限与资金

- 成员不能读取他人视频、收入或文件。
- 团长不能访问其他团队。
- 已结算数据不能修改。
- 对象存储无永久公开地址。
- 质量系数边界、无效区间合并、金额舍入和余额恒等测试通过。
- 重复执行结算、提现回调或 Worker 结果不产生重复流水。

# 18. 开发前待确认清单

## 18.1 必须由产品负责人确认

1. 质检规则 v1：硬淘汰项、五项评分和扣分值。
2. 标签树 v1：首批场景、动作、对象和工具。
3. 价格生效时间：推荐按上传完成时间锁定。
4. 返工关联：新视频是否关联原失败记录。
5. 完全重复和近似重复如何影响入库与计费。
6. 上传授权、敏感内容和数据保留规则。
7. 小程序是否只开放给已创建成员账号。

## 18.2 必须询问技术老师

1. 正式部署地区和云厂商：Cloudflare 还是境内云。
2. 一期数据库接受 D1，还是直接采用 PostgreSQL/MySQL。
3. 微信小程序选择 Taro、原生还是 uni-app。
4. 小程序最大目标视频大小和弱网体验底线。
5. AI 服务是否已经存在；接口、限流、平均耗时和单位成本。
6. AI Worker 使用 CPU、GPU 还是第三方 API；部署在哪里。
7. 是否接受 Cloudflare Queues pull consumer 由外部 Worker 拉取。
8. 原视频和派生文件的保留周期及预计月存储预算。
9. 小程序合法域名、HTTPS、备案和审核主体是否已准备。
10. 正式环境需要的备份、RPO、RTO 和告警渠道。
11. D1 迁移 PostgreSQL 的触发线是否接受本文建议。
12. 是否需要采购商数据访问位于二期，还是一期必须提前。

## 18.3 技术老师会议建议输出

会议结束后应形成一页决策记录：

- 选定云平台和地区。
- 选定数据库。
- 选定小程序框架。
- 选定队列和 Worker 方式。
- 选定对象存储和上传协议。
- 确认 AI 接口与并发。
- 确认一期单文件上限。
- 确认数据保留周期。
- 确认一期验收容量。
- 列出负责人、截止日期和未决风险。

# 19. 最终推荐

在没有新的强制条件前，建议按以下组合启动：

- Web：保留现有 React 19 + TypeScript + vinext/Next。
- 小程序：Taro + React，先完成大视频真机上传 POC。
- API：Cloudflare Workers，保持模块化单体。
- 数据库：一期 D1，严格控制大 JSON；准备 PostgreSQL 迁移边界。
- 文件：R2 私有桶 + multipart + 短期签名。
- 队列：Cloudflare Queues + 死信队列。
- 媒体：Docker FFmpeg/FFprobe Worker。
- AI：规则 + 开源检测 + 已有/第三方多模态模型的混合方案。
- 资金：日结算、不可变账本、人工提现，不接自动支付。
- 部署：开发/测试/生产隔离，关键链路可观测、可重试、可补跑。

这套方案能够最大限度复用现有原型，在约 1000 名总用户阶段保持较低运维复杂度，同时给未来切换 PostgreSQL、增加 AI Worker 和建设采购商交付能力保留清晰边界。
