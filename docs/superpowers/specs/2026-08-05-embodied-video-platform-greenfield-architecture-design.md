# 具身智能视频数据平台
## 整体需求与技术架构方案

- 文档版本：v2.0
- 编写日期：2026-08-05
- 适用对象：产品负责人、技术负责人、前端/小程序开发、后端开发、AI/数据开发、测试与运维
- 规划口径：约 1000 名总用户，Web 管理端 + 微信小程序成员端
- 文档用途：需求评审、技术选型、系统设计、开发拆分、试运行验收

> 本文把确定的业务范围、推荐技术基线、可替换候选项和需要决策的参数分开描述。未确认的业务参数应通过配置和版本管理实现，不应写死在程序中。

# 0. 执行摘要

平台一期的核心不是建设大而全的数据交易市场，而是打通一条可运营、可追溯、可结算的视频数据生产流水线：

成员采集与上传 → 媒体解析 → AI 标签与质量检测 → 人工例外处理 → 数据资产入库 → 日结算与钱包 → 人工提现

推荐技术基线：

1. Web、微信小程序和管理后台统一访问一套版本化 API。
2. 后端采用模块化单体，按身份组织、上传、处理、质量、资产和资金等领域划分模块。
3. 结构化业务数据使用托管 PostgreSQL；视频和大型结果文件使用 S3 兼容对象存储。
4. Redis 只承担缓存、限流和短期状态，不作为业务事实或资金账本。
5. 媒体处理和 AI 推理通过可靠消息队列异步执行，API 不承载长时间任务。
6. FFmpeg、规则检测、第三方模型和自建模型统一接入 AI/媒体适配层。
7. 一期采用托管容器或轻量容器平台，不引入 Kubernetes，不拆微服务。
8. 推荐后端首选 TypeScript + NestJS；若团队执行企业 Java 规范，则替换为 Spring Boot，不改变系统边界。
9. 微信小程序首选 Taro + React，但大视频选择、分片上传和弱网恢复必须通过真机验证。
10. 以 1000 名总用户规划：峰值在线 60-120 人、同时上传 10-30 个文件、业务接口短时 50-100 RPS、AI 并发 8-16 个任务。

推荐方案的关键取舍是：业务服务保持简单，视频字节绕过业务 API，计算任务异步化，资金和审计数据强一致，所有组件保留云厂商替换能力。

# 1. 产品定位与建设范围

## 1.1 产品目标

平台用于组织成员采集具身智能相关的第一视角视频，通过自动化媒体处理和 AI 质检形成可管理的数据资产，并根据有效时长和质量规则完成成员结算。

一期必须达到以下目标：

- 能够在 Web 和微信小程序完成账号登录、视频上传和结果查看。
- 单个视频可以独立进入媒体和 AI 处理流程。
- 自动生成媒体参数、内容标签、质量问题、有效时长和综合结论。
- 管理员和团长可以在权限范围内处理例外情况。
- 合格数据形成可追踪资产，结算结果形成不可重复的资金流水。
- 系统具备基本监控、告警、备份、补跑和审计能力。

## 1.2 规划阶段

| 阶段 | 目标 | 主要交付 |
|---|---|---|
| 一期 | 建立可试运行的数据生产闭环 | 成员端、管理端、上传、媒体处理、AI 质检、资产、结算、钱包、人工提现 |
| 二期 | 提升运营和数据交付效率 | 采集活动、通知、申诉、导出、采购商访问、样本申请、交付包 |
| 后续 | 根据规模建设更强的数据运营能力 | 高级检索、模型评测、自动化交付、更多采集模态和多租户能力 |

## 1.3 一期明确不做

- 客服即时通信和工单分配。
- 第三方实名认证。
- 自动付款、自动提现和支付通道。
- 发票、税费和个税代扣。
- 团长佣金、渠道差价和多级代理账户。
- 用户段位、任务抢单和用户刷视频的内容广场。
- IMU、6DoF、深度、标定文件和专用采集 App。
- 模型训练平台、数据标注平台和 GPU 集群管理平台。
- Kubernetes、多活部署和过早微服务化。

# 2. 用户、组织与权限

## 2.1 角色定义

| 角色 | 主要职责 | 默认数据范围 |
|---|---|---|
| 普通成员 | 上传视频、查看质检、查看收入、申请提现 | 仅本人 |
| 团长 | 查看本团成员和数据、处理本团未结算例外 | 仅本团队 |
| 平台管理员 | 账号、团队、规则、全平台数据、结算、提现和审计 | 全平台 |
| 采购商（二期） | 查看授权目录、申请样本、下载交付包 | 授权范围 |

一期不单独建设质检员、客服、运营和财务后台。需要岗位细分时，通过权限点和数据范围组合实现，避免复制多套后台。

## 2.2 权限模型

推荐采用 RBAC + 数据范围约束：

- RBAC 决定用户能够调用哪些功能。
- 数据范围决定用户能够访问哪些本人、团队或平台数据。
- 文件访问必须在服务端再次校验业务权限后生成短期签名地址。
- 前端菜单和按钮隐藏只用于体验优化，不能代替服务端授权。
- 用户、角色、团队、质量调整、规则、结算、提现、下架和删除必须记录审计日志。
- 成员离开团队后，历史视频、质量和资金关系继续保留。

## 3.3 视频上传与文件管理

| ID | 需求点 | 实现与验收 |
|---|---|---|
| UP-01 | 文件类型 | 一期接受 MOV、MP4；服务端检查真实容器和媒体流 |
| UP-02 | 上传批次 | 一次多选形成一个批次，每个视频形成独立提交和处理任务 |
| UP-03 | 对象存储直传 | 客户端直接上传对象存储，业务 API 不转发视频字节 |
| UP-04 | 分片上传 | 大文件使用 multipart，支持分片并发、重试、暂停和恢复 |
| UP-05 | 幂等完成 | 相同上传会话重复完成不能创建重复文件或重复提交 |
| UP-06 | 完整性校验 | 保存文件大小、校验值、分片清单和对象版本，识别传输损坏 |
| UP-07 | 真机兼容 | iOS/安卓覆盖选视频、弱网、前后台切换、失败恢复和大文件 |
| UP-08 | 私有访问 | 原视频和派生文件默认私有，预览和下载地址短期有效 |
| UP-09 | 生命周期 | 未完成分片、孤儿文件和过期临时文件可以自动清理 |
| UP-10 | 安全扫描 | 文件完成后执行容器、扩展名、大小和恶意内容基础检查 |

上传参数建议起点：

- Web 分片 16-32 MiB，每文件并发 4-6 片。
- 小程序分片 8-16 MiB，每文件并发 2-3 片。
- 100 MB 以上默认启用 multipart，最终阈值以对象存储 SDK 和真机结果确定。
- 上传会话保存 `upload_id`、对象键、分片号、ETag/校验值、文件大小和过期时间。
- 小程序按“可恢复上传”验收，不承诺切入后台后持续传输。

## 3.5 AI 标签与质量检测

| ID | 需求点 | 实现与验收 |
|---|---|---|
| AI-01 | 单视频独立任务 | 单个文件完成校验后立即入队，不等待同批其他文件 |
| AI-02 | 任务状态 | 排队、处理中、重试中、成功、系统失败分别保存 |
| AI-03 | 处理阶段 | 媒体预检、画质、内容标签、动作片段、无效区间、重复候选和综合评分 |
| AI-04 | 模型适配层 | 规则、第三方 API、开源模型和自建模型统一输出标准协议 |
| AI-05 | 版本追踪 | 每次结果记录模型、提示词/参数、代码和规则版本 |
| AI-06 | 结果不可覆盖 | 重跑产生新的处理运行记录，历史结果保持可查 |
| AI-07 | 问题证据 | 保存原因码、严重度、扣分、时间范围、证据帧和置信度 |
| AI-08 | 内容标签 | 保存场景、动作、对象、工具、视角和任务摘要 |
| AI-09 | 失败重试 | 可恢复错误自动重试，达到上限进入死信队列和人工重跑 |
| AI-10 | 失败分离 | 系统处理失败不能记为成员视频质量不合格 |
| AI-11 | 重复检测 | 文件哈希拦截完全重复；视觉近似一期只生成候选 |
| AI-12 | 成本记录 | 记录模型调用量、GPU 时间、阶段耗时和单视频处理成本 |

推荐质检分层：

1. L0 文件合法性：容器、损坏、截断和媒体参数。
2. L1 画面质量：模糊、曝光、抖动、黑屏、遮挡、静止和手部可见。
3. L2 内容理解：视角、场景、对象、工具、动作片段和动作完整性。
4. L3 重复与覆盖：完全重复、视觉近似和场景动作库存覆盖。
5. L4 综合结果：分数、硬淘汰项、无效区间、改进建议和入库结论。

# 5. 核心业务状态与数据流

## 5.1 状态拆分原则

不能使用一个 `status` 表达完整生命周期。至少拆分为：

- 上传状态：待上传 → 上传中 → 校验中 → 上传完成 / 上传失败 / 已取消。
- 处理状态：待创建 → 排队中 → 处理中 → 重试中 → 成功 / 系统失败 / 已取消。
- 质量状态：未评分 → AI 通过/不通过 → 最终通过/不通过。
- 资产状态：非资产 → 候选 → 已入库 → 已下架 / 已归档。
- 结算状态：未计价 → 待结算 → 处理中锁定 → 已入账 / 不计费关闭。
- 提现状态：待审核 → 已撤回 / 已驳回 / 待打款 → 已完成 / 打款失败。

每种状态只能由明确的命令改变，跨状态修改必须校验前置条件并记录事件。

## 5.2 端到端数据流

客户端创建上传会话 → API 写入上传记录并返回分片凭证 → 客户端直传对象存储 → API 幂等确认完成 → 事务写入提交记录与待发送事件 → 消息队列创建媒体任务 → 媒体节点生成参数和派生文件 → AI 节点执行标签与质检 → 结果校验并写入数据库和对象存储 → 例外处理与资产入库 → 日结算写入不可变账本

## 5.3 幂等与一致性

建议设置以下业务唯一键：

- 上传完成：`upload_session_id` 唯一。
- 原始文件：`storage_bucket + object_key + object_version` 唯一。
- 数据提交：`raw_file_id` 唯一。
- 处理运行：`submission_id + pipeline_version + run_no` 唯一。
- 处理结果回调：`processing_run_id + result_version` 唯一。
- 结算明细：正常结算按 `submission_id` 唯一。
- 钱包流水：`business_type + business_id + direction + sequence` 唯一。
- 日结算批次：`business_date` 唯一。
- 提现动作：`withdrawal_id + ledger_action` 唯一。

推荐使用“数据库事务 + Outbox 事件表”连接业务写入和消息队列。消费者按至少一次投递设计，通过唯一键和状态前置条件实现幂等，不依赖消息恰好只投递一次。

# 6. 技术架构设计原则

## 6.1 原则

- 业务边界优先：先按领域模块分隔，再决定是否拆服务。
- 业务事实强一致：账号、权限、状态、规则、结算和账本以关系数据库为准。
- 大文件与业务 API 分离：视频直接进入对象存储。
- 长任务异步化：转码、抽帧、模型和导出通过队列执行。
- 可替换：对象存储、消息队列、模型和云平台通过适配器隔离。
- 可追溯：任务、模型、规则、人工调整和资金均保存版本及审计。
- 可补偿：所有定时批处理和异步任务都能重试、补跑和对账。
- 适度设计：1000 名用户阶段不采用 Kubernetes，不提前拆微服务。

## 6.2 非功能目标

| 类别 | 一期目标 |
|---|---|
| 可用性 | 月度核心业务可用性目标 99.5%，计划维护时间单独公告 |
| API 性能 | 常用读接口 P95 小于 500 ms，复杂统计通过快照或异步任务 |
| 上传可靠性 | 可恢复失败分片，不因单文件失败影响同批其他文件 |
| 任务可靠性 | 至少一次投递、幂等消费、指数退避、死信和人工补跑 |
| 数据可靠性 | 资金和审计不可物理覆盖，数据库支持时间点恢复 |
| 安全 | TLS、私有对象、短期签名、最小权限、敏感信息脱敏 |
| 可观测性 | 日志、指标和链路追踪使用统一 trace_id |
| 可迁移性 | 业务代码不直接依赖某云厂商的对象、队列和密钥实现 |

# 7. 架构候选与推荐

## 7.1 方案 A：模块化单体 + 托管云组件

这是一期推荐方案。

| 维度 | 设计 |
|---|---|
| 应用 | 一个模块化 API 应用、一个定时任务进程、多个媒体/AI 工作节点 |
| 数据库 | 托管 PostgreSQL |
| 缓存 | 托管 Redis |
| 文件 | S3 兼容对象存储 |
| 消息 | 托管 RabbitMQ、SQS、RocketMQ 或同类可靠队列 |
| 部署 | 托管容器服务，API 至少两个副本 |
| 优点 | 开发快、事务清晰、运维低、可以按模块逐步拆分 |
| 风险 | 需要持续维护模块边界，避免单体内部耦合 |

适用条件：总用户数在数千至数万级、开发团队较小、业务仍在迭代、AI 计算可独立横向扩展。

## 7.2 方案 B：Serverless 业务层 + 外部计算节点

| 维度 | 设计 |
|---|---|
| 应用 | API Gateway + 函数计算，媒体/AI 使用容器节点 |
| 优点 | 空闲成本低、按请求扩展、基础设施维护少 |
| 风险 | 长事务、数据库连接、冷启动、本地调试和云厂商绑定更明显 |
| 适用 | 业务接口简单、访问波动大、团队熟悉目标云函数平台 |

该方案可以实施，但不作为默认推荐。资金、复杂后台和多阶段任务会使函数编排快速增加复杂度。

## 7.3 方案 C：微服务 + Kubernetes

| 维度 | 设计 |
|---|---|
| 应用 | 身份、上传、处理、资产、资金等独立服务，容器编排运行 |
| 优点 | 服务独立发布和扩容，适合多团队并行及大规模业务 |
| 风险 | 服务治理、分布式事务、网络、监控和运维成本显著增加 |
| 适用 | 多个独立开发团队、日提交达到万级、模块扩容差异很大 |

一期不采用。只有出现明确的组织或容量触发条件时，才从模块化单体中拆出处理编排、资产检索或资金服务。

## 7.4 三种方案对比

| 评价项 | 方案 A 模块化单体 | 方案 B Serverless | 方案 C 微服务 |
|---|---:|---:|---:|
| 一期交付速度 | 高 | 中高 | 低 |
| 业务事务实现 | 简单 | 中等 | 复杂 |
| 运维复杂度 | 低 | 中 | 高 |
| 云厂商可替换性 | 高 | 低 | 中 |
| AI 节点独立扩容 | 支持 | 支持 | 支持 |
| 1000 用户适配度 | 最合适 | 可选 | 过度 |

# 8. 推荐逻辑架构

## 8.1 分层结构

| 层级 | 组件 | 主要职责 |
|---|---|---|
| 客户端 | Web、管理后台、微信小程序 | 页面、表单、分片控制、状态展示 |
| 接入层 | CDN/WAF、负载均衡、API 网关 | HTTPS、限流、路由、防护和静态资源 |
| 业务层 | 模块化 API、定时任务进程 | 身份、权限、业务事务、签名、查询和调度 |
| 数据层 | PostgreSQL、Redis | 业务事实、账本、缓存、限流和短期状态 |
| 文件层 | 对象存储、CDN | 原视频、预览、缩略图、证据和结果文件 |
| 消息层 | 可靠队列、死信队列 | 削峰、重试、任务分发和失败隔离 |
| 计算层 | FFmpeg 工作节点、AI 工作节点 | 媒体解析、转码、抽帧、模型和特征处理 |
| 运维层 | 日志、指标、链路、告警、备份 | 运行监控、问题定位、恢复和审计 |

## 8.2 后端模块

一个代码仓库内按领域划分模块：

- Identity：账号、认证、会话和微信绑定。
- Organization：团队、成员历史、角色和数据范围。
- Submission：上传批次、上传会话、原始文件和数据提交。
- Processing：任务、阶段、重试、心跳、回调和版本。
- Quality：标签、质量结果、问题、无效区间和人工调整。
- Asset：资产、版本、下架、检索和统计快照。
- Pricing：价格规则、质量系数和计价快照。
- Settlement：日结算、补差、批次和对账。
- Wallet：钱包账户、不可变流水、冻结和提现。
- Operation：配置发布、审计、通知和系统告警。

模块之间通过应用服务接口和领域事件通信，禁止跨模块直接修改对方数据表。

## 8.3 进程划分

| 进程 | 建议副本 | 职责 |
|---|---:|---|
| API | 2 起 | 同步业务接口、签名、查询和管理操作 |
| Scheduler | 1 主 + 锁 | 结算、快照、超时回收和一致性任务 |
| Media Worker | 2 起 | FFprobe、转码、缩略图和抽帧 |
| AI Worker | 0-N | 规则、第三方模型或 GPU 推理 |
| Export Worker（二期） | 1 起 | 导出和交付包 |

Scheduler 使用数据库租约或云平台单实例保证，任务逻辑仍必须幂等。

# 9. 技术选型候选

## 9.1 后端语言与框架

| 候选 | 优点 | 代价 | 适用判断 |
|---|---|---|---|
| TypeScript + NestJS | 开发效率高、类型清晰、前后端协作顺畅、AI 辅助效果好 | CPU 密集任务必须放独立 Worker | 一期推荐 |
| Java + Spring Boot | 企业生态成熟、事务和治理能力强、人才充足 | 工程样板和交付体量略大 | 公司统一 Java 技术规范时选择 |
| Go + Gin/Fiber | 运行资源低、并发和部署简单 | 复杂业务建模与后台开发效率取决于团队经验 | 团队 Go 能力成熟时选择 |

默认建议 TypeScript + NestJS。无论选择哪种语言，接口、模块边界、数据库和异步协议保持不变。

## 9.2 Web 与小程序

| 端 | 推荐 | 候选 | 说明 |
|---|---|---|---|
| Web/管理后台 | React + TypeScript | Vue 3 + TypeScript | 由团队熟练度决定，管理后台不需要 SSR |
| UI 组件 | Ant Design | Arco Design、Element Plus | 统一主题和权限菜单，不重复造基础组件 |
| 微信小程序 | Taro + React | 微信原生、uni-app | 首周必须验证大视频和弱网恢复 |
| 状态与请求 | TanStack Query + 轻量本地状态 | 对应 Vue 生态方案 | 服务端状态以查询缓存管理，避免全局状态膨胀 |

小程序页面和 Web 只复用类型、接口客户端、校验规则和领域计算；不以复用 DOM 组件为目标。

## 9.3 数据库、缓存与消息

| 能力 | 推荐 | 候选 | 约束 |
|---|---|---|---|
| 关系数据库 | 托管 PostgreSQL | 托管 MySQL | 资金、审计和状态必须使用事务与唯一约束 |
| 数据访问 | Prisma 或 Drizzle | TypeORM、JPA、MyBatis | 由后端语言决定，迁移文件必须版本控制 |
| 缓存 | 托管 Redis | 无缓存起步 | Redis 不保存最终余额和任务事实 |
| 消息队列 | 托管 RabbitMQ | SQS、RocketMQ、TDMQ | 必须支持确认、重试、延迟/退避和死信 |
| 搜索 | PostgreSQL 索引起步 | OpenSearch/Elasticsearch | 只有组合检索和数据量出现瓶颈后再引入 |

一期不使用 Kafka。任务量和事件保留需求不足以抵消其运维复杂度。

## 9.4 对象存储与 CDN

对象存储必须支持：

- 私有桶和基于角色的访问控制。
- multipart 上传、分片列举、完成和中止。
- 服务端加密、校验值、生命周期和版本保护。
- 短期签名上传、预览和下载。
- 事件通知或与消息队列集成。

客户端只获取最小权限、短时间、限定对象键的上传凭证。业务服务保存对象键和版本，不保存永久公网地址。

## 9.5 云平台映射

| 场景 | 容器 | 数据库 | 文件 | 缓存 | 消息 |
|---|---|---|---|---|---|
| 中国大陆优先 | 阿里云 SAE/ACK Serverless 或腾讯云 TEM/TKE Serverless | RDS PostgreSQL / TencentDB PostgreSQL | OSS / COS | 云 Redis | RocketMQ / TDMQ RabbitMQ |
| 国际或多区域 | AWS ECS/Fargate | RDS PostgreSQL | S3 | ElastiCache Redis | SQS 或 Amazon MQ |
| 私有化候选 | Docker/轻量 Kubernetes | PostgreSQL 高可用 | MinIO | Redis | RabbitMQ |

一期优先使用托管容器、数据库、对象存储和消息服务。私有化部署只有在数据主权或采购要求明确时采用。

## 9.6 媒体与 AI

| 能力 | 推荐实现 |
|---|---|
| 媒体解析 | FFprobe |
| 预览与抽帧 | FFmpeg 容器 |
| L0 文件合法性 | 确定性规则 |
| L1 画质检测 | 开源检测器 + 阈值规则 |
| L2 内容理解 | 第三方多模态 API 或自建模型适配器 |
| L3 重复检测 | 文件哈希 + 轻量视觉特征候选 |
| L4 综合评分 | 版本化规则引擎 |

推荐混合方案：确定性规则负责可解释指标，多模态模型负责内容理解，规则引擎负责最终分数。模型不能直接生成钱包金额或修改资金状态。

# 10. 数据架构

## 10.1 PostgreSQL 保存

- 用户、会话、微信绑定、团队和成员历史。
- 上传批次、上传会话、文件元数据和数据提交。
- 处理任务、执行阶段、尝试次数和错误摘要。
- 标签索引、质量摘要、问题索引和无效区间。
- 人工调整、资产状态、资产版本和统计快照。
- 价格规则、计价快照、结算批次、钱包流水和提现。
- Outbox 事件、定时任务运行记录和审计日志。

## 10.2 对象存储保存

- 原始视频。
- 低码率预览、缩略图和抽帧。
- 质检证据帧。
- 完整模型输入/输出 JSON。
- 视觉特征和可重建中间文件。
- 二期导出和交付包。

## 10.3 核心数据对象

| 领域 | 核心对象 |
|---|---|
| 身份组织 | User、Credential、Session、WechatBinding、Team、TeamMembership、RolePermission |
| 上传文件 | UploadBatch、UploadSession、FilePart、RawFile、DataSubmission、DerivedFile、MediaMetadata |
| 处理任务 | ProcessingJob、ProcessingStage、ProcessingAttempt、WorkerLease、OutboxEvent |
| AI 质检 | ModelRun、PipelineVersion、LabelDefinition、VideoLabel、SegmentLabel、QualityResult、QualityIssue、InvalidInterval |
| 复核重复 | ManualReview、DuplicateCandidate、ReviewSample |
| 资产统计 | DataAsset、AssetVersion、AssetAuthorization、DistributionSnapshot、PublicSnapshot |
| 资金 | PriceRule、PricingRecord、SettlementBatch、SettlementItem、WalletAccount、LedgerEntry、WithdrawalRequest |
| 运维审计 | AuditLog、ScheduledJobRun、WorkerHeartbeat、SystemAlert、ConsistencyCheck |

数据建模原则：

- 模型原始结果、规则汇总结果和人工最终结果分开保存。
- 当前值可以缓存，但必须能追溯到不可变运行记录。
- 钱包流水只允许追加，冲正通过反向流水完成。
- 标签使用配置表和关联表，不写死为代码枚举。
- 大型 JSON 和二进制内容只在数据库保存摘要、校验值和对象键。
- 关键状态表使用乐观锁版本或条件更新，防止并发覆盖。

## 10.4 对象键

建议格式：

`{environment}/{tenant}/{submission_id}/{layer}/{version}/{filename}`

示例：

- `prod/platform/SUB123/raw/v1/source.mp4`
- `prod/platform/SUB123/preview/v1/preview.mp4`
- `prod/platform/SUB123/evidence/run-2/frame-0012.jpg`
- `prod/platform/SUB123/ai/run-2/result.json`

对象键不包含姓名、手机号、收款账号或其他个人信息。

## 10.5 索引与分区

一期重点索引：

- `data_submission(owner_id, created_at)`
- `data_submission(team_id, created_at)`
- `data_submission(processing_status, created_at)`
- `processing_job(status, available_at, priority)`
- `quality_result(submission_id, is_final)`
- `ledger_entry(wallet_id, created_at)`
- `audit_log(target_type, target_id, created_at)`

初期不做表分区。当单表达到数千万行、删除归档明显变慢或热点索引超过数据库内存时，再按月份或业务日期对审计、任务尝试和流水类表分区。

# 11. API 与异步协议

## 11.1 API 分组

| API 组 | 主要能力 |
|---|---|
| `/api/v1/auth/*` | 登录、退出、刷新、微信绑定和密码管理 |
| `/api/v1/admin/accounts/*` | 账号、角色、状态和团队分配 |
| `/api/v1/teams/*` | 团队、成员、历史和指标 |
| `/api/v1/uploads/*` | 创建会话、分片凭证、列出分片、完成和取消 |
| `/api/v1/submissions/*` | 列表、详情、状态、预览和返工关联 |
| `/api/v1/processing/*` | 队列、阶段、重跑、错误和工作节点 |
| `/api/v1/quality/*` | 标签、质量、证据、人工调整和重复候选 |
| `/api/v1/assets/*` | 资产、检索、版本、下架和统计 |
| `/api/v1/rules/*` | 标签、质量、模型和价格版本 |
| `/api/v1/settlements/*` | 预览、生成、批次、明细、补差和对账 |
| `/api/v1/wallet/*` | 余额、流水、提现申请和撤回 |
| `/api/v1/admin/withdrawals/*` | 审核、待打款、完成、驳回和失败 |
| `/api/v1/audit/*` | 审计查询和导出 |
| `/api/v1/public/*` | 脱敏统计和公开样例 |

统一要求：

- 所有接口显式版本化。
- 列表统一游标或页码分页、排序和筛选。
- 写接口支持 `Idempotency-Key`。
- 响应返回 `trace_id`，错误使用稳定业务错误码。
- 服务端对请求和响应执行 Schema 校验。
- 小程序和 Web 不复制业务服务。

## 11.2 队列消息

队列只传递小型任务信封：

- `event_id`
- `job_id`
- `submission_id`
- `pipeline_version`
- `requested_stage`
- `priority`
- `attempt`
- `trace_id`

视频、证据图和完整模型结果不进入队列。工作节点根据任务身份获取短期对象访问权限。

## 11.3 AI 结果协议

结果至少包含：

- 执行状态、阶段耗时和资源用量。
- 媒体参数。
- 视频级标签和时间片段标签。
- 分项分数、总分和质量建议。
- 硬性淘汰项。
- 无效时间区间。
- 问题、证据帧和置信度。
- 重复候选和相似度。
- 模型、提示词/参数、代码和规则版本。
- 完整结果对象键和校验值。

服务端必须拒绝缺失关键字段、超范围分数、负时间、非法区间、不存在对象键和版本不匹配的成功结果。

# 12. 1000 用户容量规划

以下数值用于技术规划，正式上线前应使用 20-50 条真实视频重新测量文件大小、时长、上传速度和处理耗时。

## 12.1 用户与并发

| 指标 | 规划值 | 设计含义 |
|---|---:|---|
| 总注册用户 | 1000 | 约 40-50 个团队 |
| 日活用户 | 100-300 | 按 10%-30% 日活估算 |
| 峰值在线 | 60-120 | 主要为列表、详情和状态查询 |
| API 常态 | 10-30 RPS | 不包含视频字节流 |
| API 短时峰值 | 50-100 RPS | 登录、刷新、批量完成和管理操作 |
| 同时上传 | 10-30 个文件 | 客户端直传对象存储 |
| AI 并发 | 8-16 个任务 | 根据单视频耗时、限流和成本调整 |

1000 名用户不会对业务 API 形成明显压力。主要容量来自上传带宽、对象存储和媒体/AI 队列。

## 12.2 视频与存储

按平均原视频 300 MB、派生文件占原始文件 30% 估算：

| 场景 | 视频/日 | 原始/日 | 原始/月 | 含派生/月 | 90 天热存储 |
|---|---:|---:|---:|---:|---:|
| 试运行 | 100 | 30 GB | 0.9 TB | 1.17 TB | 约 3.5 TB |
| 基准 | 500 | 150 GB | 4.5 TB | 5.85 TB | 约 17.6 TB |
| 压力 | 1500 | 450 GB | 13.5 TB | 17.55 TB | 约 52.7 TB |

计算公式：

- 日原始量 = 日视频数 × 平均文件大小。
- 月原始量 = 日原始量 × 30。
- 热存储 = 月原始量 ×（1 + 派生比例）× 热存储月数。

需要确认平均时长、失败视频保留周期、派生比例和冷热分层后，才能准确核算云成本。

## 12.3 数据库量级

以每个视频 20-40 KB 结构化数据估算：

- 500 视频/日约 18.25 万个视频/年，原始结构化数据约 3.7-7.3 GB/年。
- 加上索引、审计、处理尝试和资金数据，按 10-20 GB/年预留更稳妥。
- PostgreSQL 在这一量级无需分库分表，重点是索引、分页、慢查询和归档。
- 完整 AI JSON、密集帧结果、特征和图片必须进入对象存储。

## 12.4 AI 吞吐

理论每小时处理量：

`AI 并发数 × 3600 ÷ 单视频平均处理秒数`

如果平均每条视频处理 5 分钟：

- 8 并发约 96 条/小时。
- 12 并发约 144 条/小时。
- 16 并发约 192 条/小时。

500 条/日在 12 小时上传窗口内平均约 42 条/小时，8 并发有明显余量。1500 条/日平均约 125 条/小时，需要 12-16 并发作为起点。

## 12.5 一期资源起点

| 组件 | 建议起点 | 扩容依据 |
|---|---|---|
| API | 2 × 1-2 vCPU、2-4 GB | CPU、内存、P95、每实例请求量 |
| PostgreSQL | 2-4 vCPU、8 GB，开启高可用和自动备份 | 连接数、CPU、IOPS、慢查询和存储 |
| Redis | 1-2 GB 托管实例 | 命中率、内存、连接数和淘汰 |
| Media Worker | 2 × 2-4 vCPU | 队列最老等待时间和处理时长 |
| AI Worker | 8-16 并发配额 | 队列、GPU/接口限流和单视频成本 |
| 对象存储 | 按月增长和生命周期弹性使用 | 月新增、读取流量和派生比例 |

资源配置是压测起点，不是固定采购规格。

# 13. 安全、隐私与合规

一期至少落实：

- 全链路 HTTPS/TLS，生产环境禁止明文访问。
- 视频、派生文件和模型结果默认私有。
- 上传、预览和下载使用短期签名及限定对象键。
- 数据库、对象存储和备份启用服务端加密。
- 服务账号执行最小权限，不共享管理员密钥。
- 密钥放入 Secret/KMS，不进入代码、镜像、日志和小程序包。
- 收款账号脱敏显示，提现时保存收款信息快照。
- 日志不记录密码、令牌、签名地址和完整敏感字段。
- 上传前展示数据授权、禁止内容和隐私说明。
- 管理员物理删除使用独立高风险流程，保留审批和审计。
- 第三方 AI 调用前确认传输地区、保存策略、训练使用和删除能力。
- 定期执行依赖漏洞、镜像漏洞和权限策略检查。

需要业务和法务确认：

- 上传协议、数据授权主体和使用范围。
- 人脸、声音、地址、屏幕、定位和家庭场景数据的采集边界。
- 原视频、失败视频、派生文件和已交付数据的保留周期。
- 第三方模型调用和数据跨境限制。
- 用户删除请求与资金、审计和合同记录的保留边界。

# 14. 部署、发布与配置

## 14.1 环境

- `dev`：个人开发和模拟数据。
- `staging`：真实流程联调和压力验证，不执行真实打款。
- `prod`：正式数据、独立密钥、数据库、存储、队列和告警。

各环境使用相同部署模板，但资源和密钥完全隔离。

## 14.2 容器与网络

- API、Scheduler、Media Worker 和 AI Worker 分别构建 Docker 镜像。
- API 放在负载均衡后，生产至少两个副本。
- 数据库、Redis 和消息队列只允许私网访问。
- 媒体/AI 节点只通过任务身份获取短期对象权限。
- WAF、限流和上传签名接口设置独立保护策略。
- 数据库连接使用连接池并设置超时、重试上限和熔断。

## 14.3 CI/CD

推荐流水线：

1. 代码格式、静态检查和单元测试。
2. API 契约和数据库迁移检查。
3. 构建并扫描容器镜像。
4. 部署到 staging。
5. 执行端到端、迁移和基础性能检查。
6. 人工批准后滚动发布生产。
7. 发布后执行健康检查和关键业务冒烟。

数据库迁移采用向前兼容的 expand-and-contract 方法。禁止在同一发布中直接删除仍被前一应用版本读取的列。

# 15. 监控、告警与恢复

## 15.1 可观测性

推荐通过 OpenTelemetry 统一采集日志、指标和链路：

- 所有请求、任务、结算和提现携带 `trace_id`。
- 结构化日志包含环境、服务、版本、用户/团队匿名标识和业务对象 ID。
- 指标按 API、上传、队列、媒体、AI、结算、钱包和对象存储分类。
- 日志和指标不得包含完整令牌、收款账号或签名地址。

## 15.2 关键指标

- API 请求量、错误率、P50/P95/P99 延迟和数据库连接池。
- 上传成功率、分片失败率、平均上传时长和未完成上传数。
- 队列积压量、最老任务等待、重试和死信数量。
- 媒体/AI 成功率、阶段耗时、GPU/CPU 使用率和单视频成本。
- 结算成功率、异常明细、钱包对账差异和提现停留时间。
- 数据库备份状态、对象缺失、孤儿对象和一致性检查结果。

## 15.3 告警起点

- API 5xx 连续 5 分钟高于 2%。
- 上传完成失败连续 5 分钟高于 5%。
- 最老媒体/AI 任务等待超过 30 分钟。
- 可用工作节点为 0 超过 3 分钟。
- 死信队列出现新消息。
- 日结算存在未处理失败明细。
- 钱包账本汇总与账户余额不一致。
- 数据库备份失败或剩余存储低于 20%。

阈值在试运行后根据基线调整。

## 15.4 备份与恢复目标

建议一期目标：

| 数据 | 保护方式 | RPO | RTO |
|---|---|---:|---:|
| PostgreSQL | 自动备份 + 时间点恢复 + 跨可用区 | 不超过 15 分钟 | 不超过 4 小时 |
| 对象存储原始层 | 版本保护、生命周期、误删保护 | 以对象成功完成为准 | 不超过 8 小时恢复访问 |
| 配置与迁移 | 版本控制 + 发布记录 | 每次变更 | 不超过 2 小时 |
| 资金对账 | 不可变流水 + 每日对账快照 | 单笔事务 | 不超过 4 小时 |

每季度至少演练一次数据库恢复、对象重新绑定、任务补跑和钱包核对。

# 16. 测试与一期验收

## 16.1 测试层级

- 单元测试：金额、质量系数、区间合并、状态机、权限和幂等键。
- 集成测试：PostgreSQL、Redis、对象存储、消息队列和签名流程。
- 契约测试：Web/小程序 API、队列信封和 AI 结果 Schema。
- 端到端测试：登录、上传、处理、质检、结算、钱包和提现。
- 真机测试：iOS/安卓、Wi-Fi/4G/弱网、前后台切换和大文件。
- 性能测试：API 100 RPS、30 个同时上传、500 视频/日队列模型。
- 恢复测试：Worker 宕机、消息重复、数据库恢复、对象缺失和结算补跑。
- 安全测试：越权、签名滥用、上传伪造、敏感信息和依赖漏洞。

## 16.2 功能闭环验收

- 成员能够通过 Web 和小程序登录并上传 MOV/MP4。
- 单个文件完成校验后立即进入独立处理任务。
- 系统生成媒体参数、标签、质量分、问题证据和有效时长。
- 系统处理失败不会产生成员质量失败。
- 管理员和团长可以按权限处理未结算例外。
- 每日结算重复执行不会重复入账。
- 成员可以查看余额并申请提现，管理员完成线下打款状态管理。
- 已结算且最终通过的数据形成资产和公开统计快照。

## 16.3 稳定与容量验收

- 20-50 条真实样本完成端到端回归。
- Web 和小程序在网络中断后能够恢复上传。
- 单文件失败不影响同批其他文件。
- API 短时 100 RPS 不出现持续错误或明显积压。
- 500 视频/日模型下，队列在约定处理窗口内清空。
- Worker 宕机后任务能够重新领取。
- 重复消息、回调和定时任务不产生重复状态或资金流水。

## 16.4 权限与资金验收

- 成员不能读取他人视频、收入或文件。
- 团长不能访问其他团队。
- 已结算结果不能直接修改。
- 对象存储不存在永久公开地址。
- 金额边界、舍入、无效区间合并和余额恒等测试通过。
- 钱包余额等于不可变流水汇总，提现冻结和释放可对账。

# 17. 实施计划与工作量

## 17.1 开发前技术验证

优先完成四项 POC：

1. 微信小程序 100 MB、500 MB、1 GB 视频的选择、分片上传和恢复。
2. 目标对象存储 multipart、短期签名、CORS 和生命周期。
3. FFmpeg 工作节点从队列领取任务、读取对象、生成派生文件并回写结果。
4. 真实 AI 服务的输入、输出、限流、超时、单位成本和 Schema 适配。

POC 结果决定单文件上限、队列并发、云资源和排期风险。

## 17.2 一期工作包

以下为熟练开发者使用 AI 辅助、采用成熟组件、不包含模型训练的目标口径：

| 工作包 | 内容 | 基准人天 |
|---|---|---:|
| M0 | 架构 POC、工程骨架、环境和 CI/CD | 4 |
| M1 | 账号、权限、微信绑定、团队与成员 | 4 |
| M2 | 对象存储、分片上传、文件校验和媒体处理 | 6 |
| M3 | 队列、处理编排、AI 接入、结果协议和重试 | 6 |
| M4 | 标签、质量、人工例外、资产和统计 | 4 |
| M5 | 价格、结算、钱包、对账和人工提现 | 5 |
| M6 | 管理配置、审计、监控和一致性任务 | 4 |
| M7 | 微信小程序成员核心端 | 8 |
| M8 | 端到端、真机、性能、恢复和上线修复 | 5 |
| 合计 | 一期基准 | 46 |

风险预留建议 4-6 人天，单独管理，不默认计入功能完成量。主要用于小程序大视频兼容、真实 AI 协议偏差、云网络和审核材料返工。

排期参考：

- 1 名熟练全栈开发者：约 9-11 周。
- 2 名开发者并行：约 5-7 周。
- AI/算法接口、测试和运维人员能够参与时，联调风险明显降低。

上述工时不包含模型训练、云资源费用、第三方模型调用、短信、支付通道、硬件和财税咨询。

## 17.3 二期规模

二期建议按 12-18 人天规划，具体取决于采购商权限、交付包体积、导出格式和通知渠道。二期应在一期真实运行数据稳定后再锁定。

## 17.4 推荐顺序

1. 技术验证和基础设施模板。
2. 身份、权限、团队和业务数据库。
3. Web/小程序共用的上传后端和媒体处理。
4. 队列、AI、结果校验、重试和死信。
5. 质量、人工例外、资产和统计。
6. 价格、结算、钱包、对账和提现。
7. 管理配置、监控、恢复和安全加固。
8. 全链路试运行和一期验收。

# 18. 开发前决策清单

## 18.1 产品负责人确认

1. 质检规则 v1：硬淘汰项、分项评分和扣分值。
2. 标签树 v1：首批场景、动作、对象和工具。
3. 价格生效时间是否按上传完成时间锁定。
4. 返工视频是否关联原失败记录。
5. 完全重复和视觉近似如何影响入库与计费。
6. 上传授权、敏感内容和数据保留规则。
7. 小程序是否只开放给管理员创建的成员账号。

## 18.2 技术负责人确认

1. 正式部署地区、云厂商和合规要求。
2. 后端选择 NestJS、Spring Boot 还是 Go。
3. 数据库采用 PostgreSQL 还是 MySQL。
4. 微信小程序选择 Taro、原生还是 uni-app。
5. 一期目标单文件大小和弱网恢复标准。
6. AI 服务类型、接口、限流、平均耗时和单位成本。
7. AI 使用 CPU、GPU 还是第三方 API，运行区域在哪里。
8. 消息队列采用 RabbitMQ、SQS、RocketMQ 还是 TDMQ。
9. 原视频、失败视频和派生文件的保留周期及月预算。
10. 域名、HTTPS、备案、小程序审核主体和隐私材料是否准备。
11. 正式环境 RPO、RTO 和告警渠道是否接受本文起点。
12. 采购商访问放在二期，还是一期必须预留可用入口。

## 18.3 会议决策记录

技术会议结束后至少输出：

- 选定云平台、区域和网络方案。
- 选定后端语言、数据库、小程序框架和 UI 体系。
- 选定对象存储、分片参数、消息队列和 Worker 方式。
- 确认 AI 接口、并发、超时、成本和数据传输规则。
- 确认一期单文件上限、存储生命周期和验收容量。
- 确认负责人、决策日期、风险和复查时间。

# 19. 最终推荐组合

在没有强制企业技术规范的情况下，建议采用：

- Web/管理后台：React + TypeScript + Ant Design。
- 微信小程序：Taro + React，先完成大视频真机 POC。
- API：TypeScript + NestJS 模块化单体，REST API。
- 数据库：托管 PostgreSQL。
- 缓存：托管 Redis，只用于缓存、限流和短期状态。
- 文件：S3 兼容私有对象存储 + multipart + 短期签名 + 生命周期。
- 消息：托管 RabbitMQ；使用云原生队列时通过适配层替换。
- 媒体：Docker FFmpeg/FFprobe Worker。
- AI：规则 + 开源检测 + 第三方/自建多模态模型的混合方案。
- 资金：日结算、不可变账本、每日对账、人工提现。
- 部署：托管容器，API 双副本，开发/预发布/生产隔离。
- 观测：OpenTelemetry + 云监控或 Prometheus/Grafana 体系。

该组合在 1000 名总用户阶段能够保持较低的开发和运维复杂度，同时为未来拆分处理服务、扩展 AI 节点、增加搜索和建设采购交付能力保留清晰边界。
