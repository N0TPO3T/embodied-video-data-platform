# 本地持久化账号与登录完善设计

- 日期：2026-08-11
- 状态：用户已确认
- 目标：把现有账号与登录链路收口为可长期本地运行的真实功能，所有账号、会话、权限和审计信息由 PostgreSQL 持久化，不再依赖浏览器演示数据或 D1 运行时

## 1. 已确认的产品规则

- 本系统是内部角色制平台，不开放访客自助注册。
- 首次管理员固定为用户名 `admin`、初始密码 `admin123`。
- 管理员首次登录后不强制修改密码。
- 本地预置两个团长和五个数采人员，全部是真实数据库账号，不是只存在于前端的演示数据。
- 管理员可以创建和管理管理员、团长、数采人员；团长只能管理本团队数采人员；数采人员只能访问自己的数据。
- 账号、登录会话、团队归属、账号状态、密码变更和审计日志必须在服务重启、重新构建后继续保留。
- 后续项目功能默认遵守同一标准：核心业务数据进入真实后端和持久化数据库，不用浏览器内存或演示 Store 充当最终数据源。

## 2. 预置账号

首次本地安装提供以下账号：

| 角色 | 用户名 | 初始密码 | 团队 |
| --- | --- | --- | --- |
| 管理员 | `admin` | `admin123` | 无 |
| 团长 | `tuanzhang1` | `team1234` | 团队一 |
| 团长 | `tuanzhang2` | `team1234` | 团队二 |
| 数采人员 | `ceshirenyuan1`、`ceshirenyuan2`、`ceshirenyuan3` | `user1234` | 团队一 |
| 数采人员 | `ceshirenyuan4`、`ceshirenyuan5` | `user1234` | 团队二 |

这些是已知的本地初始凭据，不作为互联网部署凭据。系统不得把密码明文写入 PostgreSQL、日志、审计记录或接口响应；数据库只保存 Argon2id 摘要。若以后允许非本机访问，必须先更换全部初始密码并启用安全 Cookie。

## 3. 初始化和持久化策略

采用幂等的本地身份初始化程序：

1. API 容器启动时先执行数据库结构升级。
2. 当数据库完全没有账号时，初始化程序在一个事务中创建两个团队、一个管理员、两个团长和五个数采人员。
3. 初始化成功后，正常重启只读取已有数据，不重新生成账号，不覆盖用户修改后的名称、状态、团队或密码。
4. 初始化过程如果中途失败，事务整体回滚，不能留下半套账号。
5. 当前已有数据库通过一次明确的安装校准操作，使上述预置账号和密码达到约定状态；该操作只在本次安装时执行，不放进每次启动流程。
6. 新建账号、修改账号和修改密码继续写入同一 PostgreSQL 数据库及 Docker 命名卷。

现有的测试身份脚本保留为测试工具时，必须和正式本地初始化命令明确分开；正式启动不依赖 `EVDP_TEST_ACCOUNT_PASSWORDS_JSON`。

## 4. 登录和会话

- 登录继续使用用户名和密码，用户名按 Unicode NFKC、去除首尾空格并忽略大小写进行匹配。
- 密码使用 Argon2id 校验；不存在的账号和错误密码返回相同提示，避免泄露账号是否存在。
- 连续五次失败后锁定十五分钟；成功登录后清除失败计数。
- 登录成功生成高熵随机会话令牌，数据库只保存令牌的 SHA-256 摘要。
- 会话默认有效七天，通过 `HttpOnly`、`SameSite=Lax`、`Path=/` Cookie 保存；本地 HTTP 不设置 `Secure`，外部 HTTPS 部署必须设置。
- 退出登录删除当前会话并清除 Cookie。
- 被停用账号、过期会话和已撤销会话不能访问受保护接口。
- 所有会改变身份状态的请求继续校验可信 Web 来源，权限判断只在后端生效。

## 5. 密码与账号管理

- 每个已登录用户都可以在个人资料页修改自己的密码，需要同时提供当前密码和新密码。
- 修改本人密码成功后撤销该账号全部会话、清除当前 Cookie，并返回登录页重新登录。
- 管理员可以重置任意账号密码；团长只能重置本团队数采人员密码。
- 管理员和团长重置他人密码时不需要知道旧密码，但必须满足密码规则。
- 重置密码、停用账号、修改角色或变更团队会撤销目标账号全部会话。
- 不能停用当前登录账号，不能停用或降级最后一个启用状态的管理员。
- 密码长度保持 8–64 个字符；密码和密码摘要不进入审计详情。

本地系统不接入短信或邮件找回密码。忘记密码时，由管理员在账号管理页面重置；如果唯一管理员无法登录，使用本机维护命令明确重置管理员密码，该命令不在参数和日志中回显密码。

## 6. 权限和数据边界

- 管理员：查看全部团队和账号，创建所有角色，修改角色与团队，重置密码，启停账号，查看全部账号审计。
- 团长：查看本团队成员，创建、改名、重置和启停本团队数采人员；不能创建团长或管理员，不能转移团队。
- 数采人员：只查看本人账号和本人业务数据，不能访问账号管理接口。
- 前端隐藏按钮只用于交互体验，所有权限边界由 NestJS API 再次验证。
- 所有登录后的页面由服务端会话判断进行路由保护，不能靠浏览器本地角色字段绕过。

## 7. 审计

以下操作写入 PostgreSQL 审计日志：

- 创建账号；
- 修改显示名称、用户名、角色或团队；
- 管理员或团长重置密码；
- 用户修改自己的密码；
- 启用或停用账号；
- 本次安装校准预置账号。

审计记录包含操作者、目标、动作、时间和非敏感变更摘要，不包含明文密码、密码摘要、Cookie 或会话令牌。系统初始化和本机维护操作使用明确的 `system` 来源标识。

## 8. 前后端收口

- 浏览器登录、退出、读取会话、账号管理和修改密码统一调用 NestJS `/api/v1` 接口。
- 服务端页面只把 `evdp_session` Cookie 转发给 NestJS，不信任浏览器传入的用户对象。
- 删除不再使用的 D1 登录路由、D1 账号仓库、明文原型密码工具和对应运行时绑定，避免两套身份系统并存。
- 前端账号状态来自后端启动数据和真实接口刷新，不再从 DemoStore 读取。
- 保留现有页面视觉结构，只补齐必要的加载、错误、锁定、失效登录和修改密码反馈。

## 9. 本地运行与健康检查

- PostgreSQL 使用 Docker 命名卷保存账号和业务数据；普通 `docker compose stop`、容器重建和代码重启不会删除数据。
- API 启动前必须完成数据库连接、结构升级和首次身份初始化。
- 增加数据库 readiness 检查，只有 PostgreSQL 可连接且必要结构存在时才报告就绪。
- README 明确区分“停止服务”和“删除数据卷”；不会在日常启动脚本中执行清库操作。
- 本地默认地址保持 Web `http://localhost:3000`、API `http://localhost:4000/api/v1`。

## 10. 验收标准

实现完成后必须实际验证：

1. 从空数据库启动后，八个预置账号真实存在并可登录。
2. 管理员、团长和数采人员分别只能进入对应工作区。
3. 管理员创建新账号后，重启全部服务，账号仍存在且仍能登录。
4. 用户修改自己的密码后，旧密码和旧会话失效，新密码可登录。
5. 管理员重置密码、停用账号后，该账号旧会话立即失效。
6. 团长不能查看或修改其他团队账号，数采人员不能调用账号管理接口。
7. 五次错误密码触发锁定，接口和页面给出安全提示。
8. 数据库中没有明文密码，会话表中没有原始令牌，日志中没有凭据。
9. 删除遗留 D1 运行链路后，Web 登录和账号页面仍通过全部自动化测试。
10. 后端单元测试、接口测试、类型检查和构建通过；前端测试、类型检查、构建和关键页面渲染通过。

## 11. 当前任务边界

本次实现覆盖账号、团队、登录、会话、密码、权限、审计和身份数据持久化。视频、AI 质检、结算等模块不在本次改造范围内，但今后接线时必须遵守本设计确认的真实后端与持久化原则，不能把演示 Store 当作完成状态。
