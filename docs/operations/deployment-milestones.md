### 1.2 待完成（到云服务器生产部署的差距）

1. **Web 端无生产部署形态**：web 是 vinext（Next.js 16）应用，仓库内没有 Web 的 Dockerfile 或静态托管方案；`worker/index.ts` 表明可走 Cloudflare Workers，但"云服务器"路线需要另行决策（见决策点 D2）。
2. **无生产版编排**：当前 `compose.yaml` 是本地版——所有端口绑定 `127.0.0.1`、api 显式设置 `EVDP_ALLOW_LOCAL_DEFAULT_PASSWORDS=true`、无资源限制、无日志轮转、无外部网络接入点。
3. **无域名 / DNS / HTTPS / 反向代理 / CDN**：浏览器直传 MinIO 需要公网可达的 `MINIO_PUBLIC_ENDPOINT` 与 CORS 配置，目前只有本地地址。
4. **无生产密钥管理**：`.env` 全部是本地默认值；生产需要强随机密钥、独立管理渠道与轮换机制。
5. **无云存储容量规划**：单文件最大 2 GiB、基线 500 条/日、默认保留 180 天，对象存储按 TB 级规划；MinIO 单机 vs 云对象存储需要选型（D4）。
6. **无云级备份/恢复自动化**：README 只有本地 `pg_dump` + `minio cp` 演练；生产需要数据库快照/WAL、对象存储版本化/跨区复制与定期恢复演练。
7. **无监控、日志采集与真实告警**：只有告警阈值建议（`release-readiness.md`），未接入任何监控与告警系统。
8. **无 CD 流水线**：CI 已有，但没有构建镜像、推送镜像仓库、自动部署的环节。
9. **未做真实压测与长时间运行验收**：验收基线只写了口径，没有在真实环境执行过。
10. **安全加固未落地**：防火墙/安全组、SSH 加固、依赖与镜像漏洞扫描、密钥轮换、预设账号处理（生产启动仍会执行 `bootstrap-local-identity` 创建本地预设账号，需确认生产策略）。

> 已明确不做：真实提现/支付、客服工单、采购商门户、iPhone 录制 App、团长佣金等（见 `docs/当前项目未实际实现内容清单.md`），不影响部署范围。

## 五、服务器配置建议（Phase 1 资源规划参考）

### 5.1 负载特性（先看瓶颈）

| 组件 | 主要资源消耗 | 说明 |
| --- | --- | --- |
| media-worker | CPU 高、内存中 | FFmpeg 转码低码率 MP4 + HLS 多码率分片 + 封面/证据帧，是唯一的重 CPU 负载；容器 tmpfs 3 GiB |
| api（NestJS） | CPU/内存中 | 不承载视频流量（上传走签名直传 MinIO），主要处理鉴权、查询、签名签发 |
| ai-quality-worker | CPU 低、网络中 | 调用百炼外部 API，本地只做抽帧与结果解析；tmpfs 3 GiB |
| PostgreSQL / Redis / RabbitMQ | 内存中 | 数据量不大（提交/审计元数据），PG 分配 4~8 GB 内存即可 |
| MinIO | 磁盘大、带宽高 | 视频对象存储，容量与带宽是最大瓶颈，不是 CPU |

结论：**CPU 和内存按"够用"配置即可，真正要提前规划的是磁盘容量与公网带宽。**

### 5.2 推荐配置

| 档位 | vCPU | 内存 | 系统盘 | 数据盘（MinIO/PG） | 带宽 | 适用场景 |
| --- | --- | --- | --- | --- | --- | --- |
| 最小可用（试运行） | 4 核 | 16 GB | 80 GB SSD | 500 GB SSD | 100 Mbps（或按流量） | 内测/小团队，≤30 并发上传 |
| 推荐（一期正式） | 8 核 | 32 GB | 100 GB SSD | 2 TB 起步（见 5.3 测算） | 200 Mbps 或按流量计费 | 500 条/日基线 |
| 规模化（二期） | 计算与存储拆分 | — | — | 对象存储迁移 OSS | CDN 分发 | 业务量增长后 |

可选：Media Worker 单独一台高 CPU 实例（8~16 核），与 API/数据库分离，避免 FFmpeg 抢占业务请求资源。

### 5.3 存储容量测算（必须先算）

```
容量 = 日均视频数 × 平均文件大小 × 保留天数 × (1 + 派生文件系数)
```

- 派生文件（低码率 MP4 + HLS 分片 + 封面 + 证据帧）按原始体积的 30%~50% 估算
- 示例 A（均文件 200 MB，手机拍摄 2~5 分钟）：500 条/日 × 200 MB × 180 天 × 1.4 ≈ **25 TB**
- 示例 B（均文件 50 MB，短片段为主）：500 条/日 × 50 MB × 180 天 × 1.4 ≈ **6.3 TB**
- 结论：单机云盘撑到几个 TB 尚可；超过 5~10 TB 强烈建议直接上云对象存储（OSS/S3），省去 MinIO 单机扩容与备份的麻烦。M4 里程碑前先用真实数据测出平均文件大小再定盘。

### 5.4 带宽与网络架构

- 上传：浏览器分片直传 MinIO（API 只签发链接），公网带宽主要吃在"用户 ↔ MinIO"之间；500 条/日集中在业务时段 ≈ 持续 30~100 Mbps，峰值更高
- 下载：预览 HLS 流媒体与交付包下载走公网，产生出口流量费用；量大后上 CDN 或 OSS + CDN
- 网络拓扑：公网仅开放 80/443；MinIO 需独立域名 + HTTPS 供浏览器直传（或直接换云 OSS 免暴露）；MinIO 控制台、RabbitMQ 管理页不对公网开放
- 云厂商计费：固定带宽贵且浪费，建议"按流量计费 + 峰值带宽 200 Mbps"，再配合 CDN 降低出口成本

### 5.5 避坑点

- 不需要 GPU：AI 质检走百炼外部 API；只有未来自建大模型推理才需要 GPU
- 系统盘与数据盘分开挂载；备份（pg_dump、对象版本化）落到独立存储，不要与业务数据共用同一块盘
- x86_64 架构优先，FFmpeg 相关镜像兼容性最好
- 国内公网服务确认备案状态（2~4 周），云资源开通前先启动备案
- 先用按量/包月小规格跑通 M3~M6，压测后再按 M10 结果升配，避免前期过度购买

### 5.6 为什么推荐 8 核 / 32 GB（推导依据）

**内存 32 GB 构成（单机全包时）：**

| 占用项 | 估算 |
| --- | --- |
| media-worker 容器 tmpfs（FFmpeg 转码中间文件，RAM 内存盘） | 3 GiB |
| ai-quality-worker 容器 tmpfs（抽帧缓冲） | 3 GiB |
| api 容器 tmpfs | 4 GiB |
| PostgreSQL（元数据 + 缓冲） | 4~8 GB |
| MinIO（大对象缓冲） | 2~4 GB |
| RabbitMQ + Redis | 2~3 GB |
| Node 进程（API + 两个 Worker） | 2~3 GB |
| 操作系统 + Docker | 1~2 GB |
| 合计 | 约 24~30 GB，留 10~20% 余量 → 32 GB |

16 GB 在"多部大视频同时转码 + AI 抽帧 + 业务查询"的峰值下可能触发 OOM，Docker 会直接杀掉容器。

**CPU 8 核推导：**

- 每部视频的媒体处理要跑 3~4 次 FFmpeg（探测、黑屏/冻结扫描、960p 低码率、720p+480p 双码率 HLS、封面/证据帧）；HLS 是单次 FFmpeg 进程内同时编码两路（split 滤镜 + var_stream_map），libx264 默认按核数开线程，一部大视频就能打满全部核
- 验收基线 500 条/日 ÷ 8 小时业务窗口 ≈ 每分钟 1 条；4 核时单条处理耗时（2~5 分钟）追不上 1 条/分钟 → 队列积压
- 8 核 = 单条转码更快 + 可并行 2 路作业 + 给 API/AI Worker 留余量

**何时可以低于此配置：** 试运行/内测（日均几十条）、调低 AI 并发、接受队列低峰消化；或拆分部署（媒体 Worker 单独高 CPU 实例、对象存储上 OSS）。云服务器可随时升配，建议 4C16G 起步跑通 M3~M6，按 M10 压测数据再升到 8C32G。

### 5.7 阿里云 ECS 选配示例（cn-wulanchabu 包年包月）

在阿里云 ECS 购买向导（自定义购买 → 包年包月）逐项选择：

| 向导字段 | 建议选择 | 理由 |
| --- | --- | --- |
| 地域 | 华北3（乌兰察布） | 国内低成本区；公网服务需 ICP 备案 |
| 可用区 | 随机分配或可用区 A | 单机部署无差异 |
| 实例规格 | 目标：通用型 g8i/g7 8 vCPU / 32 GB（如 g8i.2xlarge）；起步可选 4 vCPU / 16 GB（g8i.xlarge） | 见 5.6 推导。**不要选**经济型 e 系列、突发性能型 t6/t5：FFmpeg 高负载会耗尽 CPU 积分被限速 |
| 镜像 | Ubuntu 22.04 LTS 64 位（或 24.04 / Alibaba Cloud Linux 3） | 与 Docker 及 node:22-alpine 镜像兼容性最好 |
| 系统盘 | ESSD 云盘 PL0/PL1，80~100 GB | 承载系统 + Docker + PG/Redis/RabbitMQ 数据 |
| 数据盘 | ESSD PL1，容量按 5.3 测算（500 GB~2 TB 起步） | 单独挂载给 MinIO，与系统盘隔离 |
| 网络/带宽 | 按使用流量计费，带宽峰值 100~200 Mbps；分配公网 IPv4（不必单独买 EIP） | 上传/预览按量付费更省；峰值即带宽上限 |
| 安全组 | 新建，入方向先只开 22；80/443 上线前再加 | 最小暴露原则 |
| 登录凭证 | 密钥对（推荐） | 优于密码，配合 SSH 加固 |
| 实例名称/数量/时长 | 如 evdp-prod-01；数量 1；先购 1 个月试运行 | 压测（M10）后再决定长期规格与时长 |
| 释放保护 | 开启 | 防止误删实例 |

购买后立刻执行（对应 M2/M3）：安全组仅放行 22/80/443 → SSH 密钥登录验证 → 挂载并格式化数据盘 → 安装 Docker → 启动 ICP 备案（2~4 周，尽早开始）。

### 5.8 选配审查记录（2026-08-18，华东1 杭州）

用户初选：包年包月 / 计算型 c9i.xlarge（4 vCPU / 8 GiB）/ ACL4 安全加固 / 系统盘 40 GiB PL0 / 按流量 50 Mbps / 默认安全组。

**结论：不建议，两个硬伤。**

1. **内存 8 GiB 必 OOM**：仅 compose.yaml 三个容器的 tmpfs（RAM 内存盘）合计 10 GiB（api 4G + media-worker 3G + ai-worker 3G），加上 PG/MinIO/队列/Node/OS，8 GiB 连 tmpfs 上限都装不下；FFmpeg 转码时 OOM 杀容器，任务丢失。计算型 c 系列内存配比低，应换**通用型 g9i.xlarge（4C/16G）起步，g9i.2xlarge（8C/32G）为目标**。
2. **无数据盘且系统盘 40 GiB 过小**：Docker 镜像 + 容器层 + PG 数据 + 日志很快见底，且视频对象（单文件上限 2 GiB）无处存放。应系统盘提到 80~100 GB，新增 ESSD PL1 数据盘（试运行 500 GB~1 TB，正式按 5.3 测算），挂载后 MinIO 数据目录指向数据盘。

其他项：按流量 50 Mbps 试运行可接受（带宽可随时变配上调）；ACL4 镜像可用（稳妥可选 Ubuntu 22.04）；默认安全组必须手动放行 22/80/443；实例名建议改为语义化名称。

**修正后的试运行配置**：通用型 g9i.xlarge（4C/16G）+ 系统盘 ESSD 80 GB + 数据盘 ESSD PL1 500 GB + 按流量 100 Mbps + 安全组 22/80/443。

### 5.9 存储方案调整：OSS 对象存储（2026-08-18 决策）

**决策**：对象存储从本机 MinIO 改为阿里云 OSS，云服务器不承载视频对象；服务器只跑计算（API/媒体 Worker/AI Worker）与数据库/队列。

**可行性**：后端存储层为 AWS SDK S3Client（`backend/src/storage/minio-object-storage.service.ts`），endpoint 可配置，预签名 URL、分片/多段上传均为标准 S3 协议——MinIO→OSS 是配置切换 + 验证，无需重写。

**收益**：本机不再跑 MinIO，省下 2~4 GB 内存与磁盘；服务器带宽几乎不承载视频流量（上传/预览走 OSS↔浏览器）；本机无需大容量数据盘（媒体 Worker 用 tmpfs 做处理临时区）。

**对服务器配置的影响**：
- 内存 16 GB 可行但为最低线：tmpfs 上限 10 GiB（api 4G + media-worker 3G + ai-worker 3G）+ PG/队列/Node/OS ≈ 16G 偏紧；生产 compose 调低 `AI_QUALITY_CONCURRENCY`（如 2），并监控内存水位，紧张即升 32G
- 规格注意：c9i.xlarge 是 4C/8G 固定规格；要 16G 需换 通用型 g9i.xlarge（4C/16G）或计算型 c9i.2xlarge（8C/16G）
- 系统盘 40G 偏紧，建议 60~80G（OS + Docker 镜像 + PG 数据 + 日志）
- 带宽 50 Mbps 按量足够（服务器不承载视频流量）

**OSS 接入验证清单（排入 M4/M5，做端到端冒烟：上传→媒体处理→预览→交付包）**：
- [ ] S3 兼容端点对 path-style 的支持（代码 `forcePathStyle: true`）
- [ ] 签名 region（代码写死 `us-east-1`）与 OSS 兼容签名的匹配
- [ ] 分片上传（16 MiB 分片）、预签名 URL、自定义 metadata（`expected-sha256`）
- [ ] OSS bucket CORS（浏览器直传必需）
- [ ] RAM 子账号 AccessKey 仅授权目标 bucket；bucket 不开公共读，全走预签名

**备份策略调整**：PG 每日 pg_dump 到 OSS；OSS 开启版本化/生命周期；系统盘快照可选。

## 六、风险与注意事项

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 视频存储容量快速膨胀（2 GiB/文件上限 × 500 条/日 × 180 天） | 存储成本超预算 | Phase 1 按真实平均文件大小做容量测算；设置保留期/清理策略；考虑冷存储归档 |
| 浏览器直传 MinIO 的公网暴露面 | 对象被越权访问 | 仅暴露签名 URL 所需端点，配合 API 签发、CORS 白名单；MinIO 控制台不对公网开放 |
| 本地预设账号在生产环境仍被 bootstrap 创建 | 弱口令风险 | M3 中确认生产策略：不执行 bootstrap 或立即轮换密码；生产守卫已拦截默认密码登录，仍需双保险 |
| 百炼 AI 调用产生真实费用 | 成本失控 | 设置模型调用预算与配额告警；AI Worker 并发按费用可控值配置 |
| Web 部署形态（D2）迟迟不拍板 | 阻塞 M6 | 在 M1 前必须决策 |
| 备案/合规（国内域名+公网服务） | 上线延期 | Phase 0 尽早确认是否需要 ICP 备案，备案周期 2~4 周，需提前启动 |
| 单机部署单点故障 | 服务不可用 | 一期接受单机；关键数据靠备份；二期再评估 RDS/HA |
